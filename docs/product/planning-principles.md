# 관광 의사결정 지원 기획 기준

## 2026-09-24 관련 자료 검색·원문 연결

사용자가 다음 안의 개발과 Claude Opus 5.5 설계·구현 위임, 주 담당자의 직접 검수를 요청했다.
확인된 축제·회차 또는 지역·관광자원을 검색어에 연결한다. 사용자가 `관련 자료 검색`을 선택하면
검색어를 확인·수정하고 DuckDuckGo의 일반 검색을 새 탭으로 열어 원문으로 이어간다.
검색 결과·기사 요약을 앱 내부에서 수집하거나 수치를 공공데이터 통계에 합치는 기능은 포함하지 않는다.
AI 요약은 나중에 검토한다. [기능 상세 §8](../sdlc/2-design/functional-spec.md#8-관련-자료-검색원문-연결)과
[구현·검증 상태](../validation/36-related-material-search.md)를 따른다.

## 2026-09-23 제품 이름과 두 전용 흐름

사용자가 제품 표시명을 **pickDday**(대소문자 그대로)로 확정했다. pickDday는 지방자치단체 축제 담당자가
공공 관광데이터로 지역 관광자원·방문 흐름·개최 시기를 살펴보고 관광 활성화를 위한 축제를 기획하도록 돕는
의사결정 지원 서비스다. 프로젝트·배포 식별자 `fest-compass`와 저장소 이름은 유지한다.

같은 날 사용자는 새 축제 기획을 **전용 흐름**으로 개발하도록 요청했다. 이는 이미 구현한 기존 축제 개선 흐름
(UC-FC-009) 옆에 두 번째 흐름(UC-FC-010)을 추가한다는 뜻이며 기존 흐름을 없애지 않는다.
두 흐름 모두 목표 관광객·주제·축제명·기획안·전략·메모·기록을 선행 조건으로 두지 않고 기록은 선택으로 남긴다.
관련 자료 검색은 9월 24일 후속 범위이며 AI 요약은 계속 후속 검토다. 인기 점수·테마 예측·관측하지 않은 방문객 수는 만들지 않는다. 최종 시각 디자인은 사용자가 이후 진행한다.

## 2026-09-23 설계 작업 범위

사용자는 기능·기획 개선을 진행하고, 화면 구성은 기획에 기반한 화면 목표·와이어프레임·기본 레이아웃까지
정리하도록 요청했다. 최종 UI/UX 시각 디자인은 사용자가 이를 바탕으로 개선한다.
이전 시안의 색·폰트·크기·간격은 확정 디자인으로 고정하지 않는다. 기능 의미·정보 우선순위·상태와 복구·
접근성에 필요한 행동을 명확히 전달한다. [기능 상세](../sdlc/2-design/functional-spec.md)는 이 범위의 상세 제안이다.

## 결정과 적용 범위

2026-09-22 사용자가 프로젝트 논의에서 확정하고 기록을 요청한 제품 기획 기준이다.
관광 활성화라는 목표, 지역 공무원이라는 주 사용자, 두 핵심 제품 흐름, 공공데이터를 통한
의사결정 지원과 선택적 기록의 경계를 정한다. 공모전 취지는 사용자가 제시한 기획 전제이며
이 문서는 공고·심사 규정의 별도 검증 결과가 아니다.

앞으로의 기획·설계에는 이 기준을 우선 적용한다. 기존 화면·코드의 실제 동작과 검증 이력은
그대로 구분한다. 이 결정 기록은 두 제품의 첫 화면·흐름 개편이나 데이터 추가 구현의 완료를 뜻하지 않는다.

## 목표·사용자·핵심 가치

**지역 공무원이 다양한 공공데이터를 활용해 지역 관광 활성화에 기여할 축제를 기획·개선하도록 돕는다.**

- 프로젝트는 한국관광공사의 관광데이터 활용 공모전 출품작이다. 국내·지역 관광 활성화를 고정 목표로 둔다.
- 주 사용자는 축제를 기획하고 운영하는 지역 공무원이다. 이벤트 기획 전문성을 전제로 화면이나 설명을 구성하지 않는다.
- 지역 소비·주민 참여·지역 인지도는 관광 활성화와의 관계 안에서 다룬다.
- 한국관광공사뿐 아니라 한국 정부·공공기관의 다양한 공공데이터를 활용 대상으로 검토한다.
- 핵심 가치는 필요한 데이터를 확보·정제하고, 질문에 맞게 가공·연결·시각화해 판단에 쓸 수 있도록 제공하는 것이다.
- 기획 가이드는 고려할 사항과 자료 해석·추가 확인을 돕는다. 세부 구성은 후속 논의에서 정한다.

## 두 핵심 제품 흐름

첫 화면에서 두 상황을 구분해 각 목적에 맞는 정보 탐색·비교 흐름으로 진입한다.
이 구분은 사용자 목적에 따른 제품 구분이며 코드·배포·저장소 분리 여부를 결정하지 않는다. 두 흐름은 한 서비스 안에 함께 제공한다.

| 제품 흐름 | 사용자의 상황 | 시스템의 지원 초점 |
|---|---|---|
| 기존 축제 개선 | 기존 축제의 다음 회차를 준비한다. | 확보한 과거·현재 자료와 주변 여건을 비교해 관광 활성화 기여를 높일 변경을 판단하도록 돕는다. |
| 새 축제 기획 | 지역의 관광 기회를 활용할 축제를 구상한다. | 지역 자원·관광 추세·주변 행사·실행 여건을 연결해 주제·장소·시기 등을 탐색하고 비교하도록 돕는다. |

두 흐름 모두 사용자 작성 기획안·과거 실적 파일·저장된 메모 없이 자료 탐색을 시작할 수 있어야 한다.
확보한 공공자료로 의미 있는 정보와 비교 기능을 구성하고, 자료 차이는 정보의 선택·배치와 시각적 위계로 전달한다.
미확인 값을 만들거나 0으로 바꾸지 않으며, 내부 수집·검증 상태를 사용자용 제약 안내문으로 옮기지 않는다.

## 첫 버전의 범위와 구현 순서

2026-09-22 후속 논의에서 사용자가 확정했다. 기존 축제 개선부터 기능·데이터 대응과 화면 흐름을 정리하고,
공공데이터를 활용한 핵심 기능을 구현한 뒤 뉴스 연결을 진행한다.

| 순서·범위 | 결정 |
|---|---|
| 우선 구현 | 공공데이터를 목적에 맞게 정제·연결한 조회·비교·시각화. 관광 활성화 판단에 필요한 정보를 제공한다. |
| 핵심 기능 구현 뒤 | 축제·회차와 관련된 뉴스 검색과 원문 연결. 첫 버전 핵심 기능의 선행 조건으로 두지 않는다. |
| 첫 버전에서 제외 | 외부 보도자료·뉴스의 수치를 AI 등으로 추출·정규화해 핵심 통계에 자동 반영하는 기능. |
| 나중에 검토 | AI 요약. 모델 선정·성능 시험·요약 구현을 현재 작업 범위에 넣지 않는다. |

뉴스를 아예 활용하지 않기로 한 결정은 아니다. 이후 검색·원문 연결만으로 우선 제공하고 AI 요약은 별도로 검토한다.
검색 제공자를 네이버로 고정하지 않는다. 9월 24일 승인된 후속 개발에서 DuckDuckGo의 일반 검색 링크를 선택했다.
공식 `q` URL 형식을 사용하며 API·자동 수집 도입이나 기사 품질 보증으로 확대하지 않는다. 확인 근거는 [기록36](../validation/36-related-material-search.md)에 있다.
이 결정은 후보 제공자의 API·수집·AI 이용 가능 여부를 검증한 결과가 아니다.
기존에 검수한 공개 문서·비용 사례를 삭제하거나 모든 비정형 공공자료를 배제하는 결정으로 확대하지 않는다.

## 기존 축제 첫 버전의 핵심 기능

2026-09-22 사용자가 아래 세 기능을 모두 첫 버전의 핵심으로 확정했다.

| 핵심 기능 | 사용자가 판단할 내용 | 제공할 정보 |
|---|---|---|
| 과거 방문 흐름 비교 | 축제 개최 시기에 지역 방문이 어떻게 달라졌는가 | 지역 일별 방문 추세, 축제 기간 표시, 이전 회차·주변 기간 비교 |
| 주변 관광자원 연결 | 축제 방문을 지역 관광으로 이어갈 방법은 무엇인가 | 주변 관광지·문화시설과 위치, 연계 후보 탐색 |
| 다음 개최 시기 검토 | 다음 회차의 시기를 정할 때 무엇을 고려해야 하는가 | 계절별 방문 추세, 공휴일, 주변 행사 일정 |

- **제공 범위:** 전국의 기본 관광정보·행사 탐색을 제공하고, 과거 분석은 자료가 확보된 지역부터 확장한다. 지역별 화면은 제공 가능한 정보로 구성한다.
- **첫 화면과 탐색:** 축제를 선택한 뒤 과거 방문 흐름을 먼저 보여주고 주변 관광자원·다음 개최 시기로 연결한다. 이는 정보의 우선순위이며, 각 기능을 자유롭게 이동할 수 있어야 한다.
- **입력과 기록:** 축제·회차·지역·기간 등 조회에 필요한 조건만 사용한다. 목적·선택 이유·메모·기획안 작성이나 저장을 탐색의 조건으로 요구하지 않는다.
- **추가 분석:** 관광객 성별·연령·소비·숙박 분석은 축제별 실제 자료 확보 가능성을 확인한 뒤 추가 범위를 정한다.
- **설계 경계:** 지역 방문 추세를 행사장 입장객이나 축제의 인과 효과로 바꾸지 않는다. 주변 자원은 연계 후보이며 실제 이동 경로로 단정하지 않는다. 개최 시기 검토는 비교 근거를 제공하며 최적 날짜를 확정하지 않는다.

이 절은 기능 범위와 탐색 방향의 확정이다. 각 기능의 상세 지표·비교 기준·데이터 연결·화면 구성·유스케이스는 다음 설계에서 구체화한다.

## 시스템이 할 일과 사용자가 판단할 일

| 구분 | 경계 |
|---|---|
| 시스템의 책임 | 자료 확보·정제, 정의·기간·지역·단위 정합 확인, 목적에 맞는 가공·연결·비교·시각화. 지표의 의미는 제목·단위·기간과 화면 구성으로 전달하고 출처·세부 계산은 필요할 때 확인할 수 있게 제공 |
| 사용자의 판단 | 목표 관광객 선정, 방문 매력·주제 구상, 최종 장소·일정·규모 선택, 조직 내 협의·실행 결정 |
| 선택적 기록 | 목표·아이디어·답변·선택 이유·메모·기획안·결과를 원할 때 남기고 다음 회차에 재사용 |
| 필수 입력의 범위 | 특정 조회·계산에 실제로 필요한 지역·기간·비교 대상 등 최소 조건. 전략적 질문의 서술형 답변이나 저장 완료를 선행 조건으로 삼지 않음 |

시스템은 데이터만으로 '누구를 유치해야 하는가', '왜 찾아올 것인가'의 정답을 확정하지 않는다.
관련 자료와 검토 관점을 제공하고 판단을 돕는다. 자료에 없는 동기·수요·관광 효과를 임의로 채우지 않는다.

**사용자의 답변과 기록은 선택 사항이다.** 목표 관광객·방문 이유·선택 사유를 쓰지 않거나
기획안을 저장하지 않아도 핵심 데이터 조회·비교·시각화를 이용할 수 있어야 한다.
필수 기록 단계를 건너뛰는 별도 우회 경로에 의존하지 않고, 기록 없이도 유용한 기본 경험을 설계한다.
기록을 선택한 경우에도 기획 질문 전체의 답변 완료를 강제하지 않는다.
파일 구조·값의 형식·참조 무결성 검사는 기록 내용의 업무적 완성도와 구분한다.

## 핵심 질문은 정보 설계의 기준

다음 질문은 시스템이 어떤 자료를 보여줄지 정하는 기준이다. 사용자가 모두 답하거나
시스템에 제출해야 할 설문·입력 체크리스트가 아니다.
아래 자료는 후속 조사에서 가용성·입도·갱신 주기·해석 범위를 확인할 후보이며 제공을 보장하지 않는다.

| 판단을 돕는 질문 | 필요한 정보의 검토 방향 | 데이터로 확정하지 않을 것 |
|---|---|---|
| 어떤 관광객의 방문을 유도할 것인가? | 확보 가능한 방문 특성·지역 관광 추세·접근 여건을 비교 | 최적 목표 관광객, 개인의 방문 의도 |

## 데이터 활용의 설계 원칙

1. 판단 질문 → 필요한 정보 → 공공데이터의 실제 가용성 → 정제·연결·가공 → 비교·시각화·해석 안내 순으로 검토한다.
2. 지역·기간·단위·집계 정의가 다른 자료는 비교 가능 여부부터 확인한다. 원자료·가공값·사용자 가정을 구분한다.
3. 출처·기준일·자료 범위·가공 방법은 필요한 깊이로 확인할 수 있게 제공한다. 자료가 없는 항목을 경고 카드로 나열하지 않으며, 결측을 0으로 바꾸거나 미확보를 관광 수요 없음으로 해석하지 않는다.
4. 가이드는 무엇을 고려하고 자료를 어떻게 읽으며 어디까지 판단할 수 있는지 안내한다. 답변 작성·저장 없이 읽을 수 있어야 한다.
5. 제품의 가치는 기록 개수나 기획안 작성 완료율보다 필요한 정보의 확보·비교·이해와 의사결정 지원으로 검토한다. 구체적인 평가 방법은 후속으로 정한다.
