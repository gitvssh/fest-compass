# 현행 기능·문서·데이터 점검

## 2026-09-23 제품 이름과 새 축제 흐름 개발

제품 표시명은 **pickDday**다. 지방자치단체 축제 담당자가 공공 관광데이터로 지역 관광자원·방문 흐름·개최 시기를
살펴보고 관광 활성화를 위한 축제를 기획하도록 돕는 의사결정 지원 서비스다. 프로젝트·배포 식별자 `fest-compass`와
공개 주소, 저장소 이름은 그대로다.

| 대상 | 상태 |
|---|---|
| 기존 축제 개선 흐름 | 사용 가능 — 아래 최신 기존 축제 구현과 검증 기록34 |
| 새 축제 기획 전용 흐름 (`/new`에서 지역 선택 → `/new/{지역코드}/resources·visits·timing`) | 사용 가능 — 자동 시험 통과·공개 운영 확인 완료. 실행 기록은 [검증 기록35](../validation/35-pickdday-new-festival.md) |
| 공개 서비스의 새 축제 선택 | 첫 화면과 새 축제 메뉴가 `/new` 지역 선택으로 연결 |

새 축제 전용 흐름은 두 번째 흐름으로 추가하며 기존 축제 흐름을 대체하지 않는다.

### 새 축제 흐름의 구현·자동 검증

- **지역 선택과 주소:** `/new`에서 시도·시군구만 고른다. 주소는 5자리 행정 코드이며 논산 `/new/44230`,
  세종 `/new/36110`(지역 목록의 `36110/36110` 행)이다. 모르는 코드는 `지역 다시 고르기`로 돌아간다.
- **세 화면:** 관광자원이 먼저 열리고 `지역 관광자원 / 지역 방문 흐름 / 개최 시기`를 순서 없이 오간다.
  축제명·주제·대상·이유·기획안 작성이나 저장이 필요 없다. 주소는 지역과 `types`·`year`·`month`만 보존하고
  함께 보기·상세·기준점·반경·후보 기간은 같은 탭 안의 임시 선택이다. 브라우저 저장소와 쓰기 요청은 없다.
- **관광자원:** 기존 관광지·문화시설 조회와 지도를 재사용한다. 함께 보기는 최대 두 곳, 거리는 기준점을 정한 뒤에만 보인다.
  소개는 새 조회 `/api/new/resource-detail`이 TourAPI `detailCommon2`에서 같은 ID·유형·지역을 확인한 뒤 일반 텍스트로 준다.
  소개가 없으면 칸을 생략하고, 실패하면 상세 안에서 다시 불러온다. 소개 수집 시각은 목록 수집 시각과 따로 표시한다.
- **방문 흐름:** 새 조회 `/api/new/visits`가 기존 월별·일별 방문에 요일 평균을 더한다. 선택 연도의 모든 날짜 값이 있을 때만
  일곱 요일 평균을 만들고, 값이 0인 날은 관측값으로 센다. 논산·공주·임실만 방문 자료가 있으며(2023~2025 완전, 논산 2026 부분)
  시군구 전체 외지인 방문 추정이지 시설 방문자·축제 입장객이 아니다.
- **개최 시기:** 기존 달력과 후보 기간(0~2개, 선택)을 재사용한다. 방문 흐름의 월 표에서는 그 실제 연월 달력만 연다.
- **검증:** 단위 280건·타입·빌드·전체 headless 18개 스크립트 통과. 새 축제 [TS-FC-010](../sdlc/3-testing/scenarios/TS-FC-010.md)은
  AC1~14의 37개 확인 항목을 통과했다. 공개 운영 확인을 마쳤으며 최종 시각 디자인과 실제 담당자 관찰은 후속이다.

## 최신 기존 축제 구현

첫 화면에서 두 목적을 선택하고 기존 축제는 `/existing/search`에서 축제를 찾는다.
과거 방문 흐름·현재 주변 관광자원·개최 시기를 기록 없이 오간다. 현재 등록 항목과 보관 축제는
검증한 식별 관계만 연결하며 현재 연결표에 등록된 관계가 없어 별도 검색 결과로 제공한다.
논산·임실·공주의 확인된 7개 회차와 일정이 확인되지 않은 원주 1회차를 서로 다른 상태로 다룬다.

공개 중인 버전의 새 축제 선택은 `/new` 지역 선택으로 연결한다. 새 축제 전용 세 화면은 위 절처럼 사용 가능이다.
Foundry 소개 자료의 앱 연결, 남은 CSV 지표 연결과 뉴스 검색은 후속이다. 아래 9월 22일 점검·저장소 통합 이력과 구분해
[기존 축제 검증 기록](../validation/34-existing-festival-journey.md)에서 최신 실행 결과와 공개 반영 상태를 확인한다.

## 2026-09-23 통합 추가

아래 9월 22일 점검은 그 시점의 기록으로 유지하고, 9월 23일 저장소 통합에서 달라진 부분만 여기와 표에 덧붙인다.
통합 범위와 경계는 [저장소 통합 보고](../ops/repository-consolidation.md)를 따른다.

- **새 화면 `/compare/annual` — 사용 가능.** 문화관광축제 26곳의 개최연도별 방문을 개최기간 일평균(기본)과
  기간 합계로 보여 준다. 값은 축제가 열린 행정동의 통신 기반 방문 추정이며 행사장 입장객이 아니다.
  2018·2019·2022~2025만 있고 2020·2021은 자료가 없다. 논산딸기축제는 목록에 없다.
  상세는 [데이터 현황](../research/2026-09-data-inventory.md#축제-개최기간-연도별-방문-추이-연결)에 있다.
- **데이터랩 원본 — 부분 연결.** CSV 304개와 문서 5개를 [원본 보관 폴더](../research/imported/hkjin-plan-03/README.md)로
  바이트 그대로 가져왔다. 이 중 연도별 방문 추이 26개만 위 화면에 연결했다. 성·연령·목적지 검색·주요 지표·지역 방문·소비 CSV는 보존만 했다.
- **검증 상태.** 전체 단위 시험 239건, 타입·빌드, headless 브라우저 16개 스크립트와 배포 계약·인프라 시험 40건을 통과했다. 공개 운영의 실제 수치·행사 CSV도 확인했으며 [통합 보고](../ops/repository-consolidation.md#검증-결과)에서 최종 상태를 확인한다.
- **행사 달력·메뉴·CSV.** 관광지도에서 같은 행사 선택을 달력·지도·목록·상세로 연결하고, 조회 조건과 월을 주소로 복원한다. 관광지도·현재 행사 비교에 CSV를 추가했으며 `/compare`에서 연도별 방문 화면으로 이동한다. 현재 메뉴 표시도 실제 경로를 따른다.
- **통합 직후 상태:** 당시 v7 두 목적 전체 흐름은 개발 필요였다. 후속 기존 축제 구현은 위 최신 절을 따른다.

## 결론과 확인 범위

9월 22일에는 지역 조회·축제 비교·근거 보관·개인 기획·예산·결과가 구현돼 있었고 첫 화면은 기능별 진입을 나열했다.
이후 목적 선택과 기존 축제 흐름을 구현했으며 새 축제 전용 흐름은 사용 가능이다.
지역·비교 조회는 전략 질문에 답하거나 기획을 기록하지 않아도 이용할 수 있다.

2026-09-22에 `pick-d-day`의 기준 커밋 `139dc62` 코드와 문서, 저장소 CSV, Foundry 실보유량,
공공기관의 공식 제공 문서를 대조했다. 문서·흐름·현행 데이터·Foundry·공식 후보의 다섯 분야를
서브에이전트가 Cursor Agent의 `cursor-grok-4.6-high`로 조사하고, 최종 정리는 원본을 직접 대조해 검수했다.
외부 자료는 공식 원문을 확보해 Grok에 전달하는 방식도 사용했다. 모델의 초안을 검증 증거로 대신하지 않는다.

이번 점검은 코드·파일·DB 읽기와 공식 문서 확인이다. 앱 전체 실행, 브라우저·접근성 시험, 운영 API 실호출,
담당자 관찰은 재실행하지 않았다. 아래 **사용 가능**은 구현 및 기존 검증 근거가 있다는 뜻이며 오늘의 운영 정상 보장은 아니다.
문서 갱신은 앱 기능·운영 배포·데이터 수집을 변경하지 않는다.

읽는 순서는 [확정 기획 기준](../product/planning-principles.md) → 이 문서 →
[데이터 현황](../research/2026-09-data-inventory.md)이다. 저장소 통합 경계는 [통합 보고](../ops/repository-consolidation.md),
담당자 확인 질문은 [인터뷰 질문지](../research/festival-officer-interview.md)에 있다. 과거 시안과 게시 이력은
[기획 검수 안내](2026-09-planning-review.md)에서 찾는다.

같은 날 후속 작업에서 기존 축제의 [세 핵심 화면 v5](../sdlc/2-design/screens.md)와
[실제 지표·가공 연결](../sdlc/2-design/data-visualization.md)을 설계했다. 아래 표는 현행 코드의 상태다.
설계 문서가 있다는 사실은 구현을 뜻하지 않으며 각 행의 상태 표시를 따른다.

## 기록 없이 이용하는 범위와 재검토할 조건

- 관광객 유형·방문 이유·사업 목적 작성은 지역 탐색과 비교의 선행 조건이 아니다.
- 초안 저장·일반 보관본과 **기획안으로 보관**은 다른 동작이다. 두 후보와 선택 이유 조건은 후자에만 적용된다.
  개인 결과 입력이 이 기획안을 참조하므로 해당 조건의 영향이 결과 기록까지 이어진다.
- 기획 초안에 미저장 변경이 있으면 내부 링크 이동을 막는 처리가 있다. 조회 자체가 기록을 강제한다는 뜻은 아니다.
- 지역 근거·비교 근거·개인 기획·개인 운영의 저장과 파일 복원은 분리돼 있다. 근거→기획 연결은 이미 존재하지만
  모든 작업공간을 통합한 파일이나 기획→운영 자동 이전 기능은 아니다.

[기획 원칙](../product/planning-principles.md)에 맞춘 필수값·이동·결과 시작 조건의 개편은 다음 설계 과제다.
현행 제약을 새 원칙으로 승인한 것으로 읽거나, 문구만 바꿔 구현도 달라졌다고 판단하지 않는다.

## 다음 작업의 시작점

아래는 9월 22일에 정리한 기획 검토 순서다. 이후 기존 축제 구현·검증을 마쳤고 새 축제 전용 흐름은 사용 가능이다.

1. **두 목적의 정보·데이터 대응표**: 사용자 판단 → 보여줄 정보 → 원천/보유 범위 → 가공·결합 → 해석 한계.
   기존 개선에는 회차·방문 특성·주변 관광 연결, 신규 기획에는 지역 자원·방문 계절성·주변 일정·접근 여건을 검토 후보로 둔다.
2. **기록 없는 기본 여정**: 지역·기간·비교 대상 등 최소 조회 조건과 전략적 질문을 분리하고, 조회·비교만으로 끝낼 수 있게 설계한다.
3. **기존 기능 재사용과 선택 기록**: 세 작업공간의 역할, 기획안 조건, 개인 결과 시작 조건, 근거 재사용·내보내기를 검토한다.
4. **두 목적별 IA·flow·UC·인수 기준**을 정리한 뒤 화면 구성·UI·차트 상세와 실제 담당자 검증 과제를 설계한다.

자동 관광객 선정·방문 이유 확정·성과 인과 추정·새로운 필수 설문은 이번 조사에서 도출한 기능이 아니다.
