## 1. FR-EVD 근거·가정

### FR-EVD-1. 근거 스냅샷 수집 [구현됨, 조회기간 변경 D4]

- 트리거: 축제 생성·복제 직후 자동 + SCR-02 "KTO 다시 불러오기" 수동 (ACT-08)
- 동작: 기존 관측 스냅샷 전체 stale=true → API별 신규 스냅샷 생성 (조회 대상·기간은 05 §1.4)
- 모든 스냅샷 필수 저장 항목: apiName, sourceUrl, baseDate, fetchedAt, aggregation(집계정의),
  status(success/empty/error), interpretation(허용 해석), prohibition(금지 해석), valueJson
- 오류 시: 해당 API만 status=error로 저장하고 계속 진행. 전체 중단 금지.
- 키 없음: 호출 없이 DataQuality(issue=missing, status=key_absent) 1행 기록 후 정상 종료.

### FR-EVD-2. 신규 축제의 기본 골격 [구현됨]

축제 생성 시 자동 생성:
- 가정 4행(v1): inflow(빈 값), peakRatio(기본 0.35), dwellHours(빈 값), operatingHours(기본 8)
- 시나리오 3종: 보수안(셔틀2·주차4·회차3), 기본안(셔틀2·주차4·회차3), 확대안(셔틀3·주차6·회차3)
- labelLevel=L0, isExample=true (실조직 파일럿 전까지 모든 축제는 예시 취급)

기본값 근거: 피크비율 0.35 = 3일 운영 중 토요일 오후 피크 가정(시드와 동일), 운영시간 8h = 10:00–18:00.
이 기본값은 "가정" 배지·작성자("기본값")와 함께 저장되어 사용자 값과 구분된다.

### FR-EVD-3. 가정 세트 버저닝 [변경 D7]

- 저장 1회 = inflow·peakRatio·dwellHours·operatingHours 4행을 **같은 version 번호**로 추가 저장(append-only).
- 새 version = 현재 최대 version + 1. 삭제·수정 없음(이력 보존).
- "최신 가정"은 각 item의 최대 version 행. 보고서·계산은 항상 최신 세트를 쓰고 세트 번호를 표기한다.
- 마이그레이션: 기존 데이터는 item별 최신 행을 v1 세트로 간주(정합 스크립트 불필요 — 조회 로직이 max version을 취하면 됨).

**현재 구현과의 차이**: `updateAssumptionsAction`이 inflow만 version+1, 나머지는 version 1 고정
→ 4행 모두 동일 신규 version으로 저장하도록 수정.

### FR-EVD-4. 가정 입력 검증 [신규]

| 규칙 | 위반 시 |
|---|---|
| inflowMin ≤ inflowBase ≤ inflowMax (입력된 값 사이에서만 비교) | 저장 거부 + "최소 ≤ 기준 ≤ 최대 순서여야 합니다" |
| 유입 ≥ 0, 체류·운영시간 0 < x ≤ 24, 피크비율 0 < x ≤ 1 | 저장 거부 |
| 빈 필드 | 허용. null 저장(0 치환 금지) |

서버 액션에서 검증한다(브라우저 검증은 보조). 거부 시 입력값 유지.

## 2. FR-CAL 수용 계산 [구현됨 — 2026-08-30 교정 반영]

### FR-CAL-1. 계산식 (lib/calc/capacity.ts — 단일 진실 원천)

```text
피크 동시체류 = 유입가정 × 피크비율 × (평균체류시간 / 운영시간)
수용여유     = 승인수용량 − 피크동시체류
점유율       = 피크동시체류 / 승인수용량
```

- 입력이 하나라도 결측이면 해당 산출값은 null (0 아님).
- 계산 결과에는 항상 formula 문자열과 입력값 스냅샷이 함께 저장된다(역추적).

**작동 예 (시드 검증값 — 단위 테스트와 일치해야 함)**:
유입 18,000 × 0.35 × (2.5/8) = 피크 1,968.75명 · 여유 2,500−1,968.75 = 531.25명 · 점유율 78.75%
유입 26,000 → 피크 2,843.75명 · 여유 −343.75명 · 점유율 113.75% (초과)

### FR-CAL-2. 안전 계산 활성 조건

`safetyEnabled = 승인수용량 > 0 AND 기준문서 존재 AND 승인자 존재 (hasApprovalBasis)`
- false면 수용여유·점유율·경고를 계산하지 않고(null) 화면에 꺼진 이유를 명시한다.
- 피크 동시체류 자체는 수용량과 무관하므로 계산한다.

### FR-CAL-3. 점유율 경고 단계

| 단계 | 조건 | 화면 문구(변경 금지) |
|---|---|---|
| off | 계산 꺼짐 | "수용량 기준이 없어 여유 경고를 계산하지 않습니다." |
| ok | < 0.85 | "가정 기준 여유 있음." |
| watch | 0.85 ≤ x ≤ 1 | "가정 기준 점유율이 높습니다. 확대 운영 대안을 검토하세요." |
| over | > 1 | "가정 기준으로 승인 수용량을 넘습니다. 자동 안전판단이 아니라 비교 신호입니다." |

임계 0.85의 근거: 행안부 지역축제장 안전관리 매뉴얼의 혼잡 관리 관행을 참고한 **내부 비교 신호**이며
법적 기준이 아니다 — 화면·문서에서 "안전 판단"으로 표현하지 않는다(기획서 §8.4). 임계값은
`occupancyWarning`에 상수로 두되 코드 주석에 이 단락을 참조로 남긴다.

## 3. FR-SCN 시나리오 [변경 D1]

### FR-SCN-1. 시나리오 정의

- 시나리오 = **운영자원 대안**. 비교 변수: 셔틀 대수, 주차 안내 인력, 회차(sessions), 동선 메모(routeNote), 구역(zone).
- 유입 수요는 시나리오의 속성이 아니다. 수요 불확실성은 가정 세트(min/base/max)가 담당한다.

### FR-SCN-2. 매트릭스 평가

- 각 축제의 계산은 유입 3값(min/base/max) 각각에 대해 FR-CAL-1을 수행한다 → 결과 3점.
- 점유율·여유는 유입값의 함수(자원과 무관)이므로 매트릭스 상단에 1회 표시하고,
  시나리오 카드는 "최대 유입에서의 경고 수준 + 이 안의 대응 자원"을 연결해 보여준다(03 §SCR-03).
- 저장 형식: `Scenario.resultJson = { byInflow: { min: CapacityResult, base: ..., max: ... } }`,
  `formulaJson`은 기존처럼 formula+inputs.
- **현재 구현과의 차이**: `persistScenarioCalcs`·`scenarioResults`의 `byKind`(보수=min, 기본/확대=base) 로직 폐기.

### FR-SCN-3. 자원 인라인 수정 [신규] (ACT-05a)

- SCR-03에서 시나리오별 셔틀·주차·회차·routeNote를 수정 저장할 수 있다.
- 저장 시 재계산·resultJson 갱신. 수정 이력은 MVP에서 남기지 않는다(결정만 이력 대상).

### FR-SCN-4. 결정 기록 [구현됨, 요약 보강]

- 필수: 이유, 승인자. 누락 시 거부.
- changeSummary는 자원 전 항목을 포함한다: "{이름}: 셔틀 {n}대, 주차 안내 {n}명, 회차 {n}회{, 동선: routeNote}".
  [변경 — 현재 셔틀·주차만]
- 재결정 시 새 Decision 추가(append-only). 최신 결정이 "현재 선택"이며 과거 결정은 이력으로 표시.

## 4. FR-TRG 대응 트리거 [신규 D2]

- OperationTrigger 생성: condition(조건·임계 설명), plannedAction(대응 조치), owner(책임자) — 전부 필수.
- 수정·삭제는 MVP 범위 밖(잘못 등록 시 새로 등록 — 원장 정신과 일치).
- FieldAction 저장 시 triggerId(선택)로 연결. 연결된 트리거는 "실행됨 {occurredAt}" 표시.
- 보고서 §3.5에 트리거별 실행 여부가 나온다: 계획된 대응의 적중률이 다음 행사 학습 자료가 된다.

## 5. FR-LGR 원장

### FR-LGR-1. 현장 조치 [변경]
- 필수: occurredAt(형식 "YYYY-MM-DD HH:mm" — datetime-local 입력), action. trigger/triggerId·actor 선택.
- 형식 위반·필수 누락 시 거부. [구현·회귀검증됨]

### FR-LGR-2. 실측 입력 [변경 D6]
- 필드: metric(필수), plannedValue, actualValue, unit, source, measureMethod, granularity(total|hourly|zone, 기본 total), bucketLabel.
- granularity가 hourly 또는 zone이면 bucketLabel(예: `13:00–14:00`, `A구역`)이 필수다. 같은 metric·unit·granularity 안에서 실제값이 가장 큰 구간만 피크 배지로 표시한다.
- kind="measured", confirmed=true로 저장. 라벨 전이는 FR-LBL.
- 출처가 비어도 저장은 허용하되 화면·보고서에 "없음"으로 그대로 노출한다(출처 없음을 숨기지 않는다).

### FR-LGR-4. CSV 실측 업로드 [신규 P2]
- 1행 = 1 Outcome. 헤더: metric,plannedValue,actualValue,unit,source,measureMethod,granularity,bucketLabel.
- 파싱 실패 행은 건너뛰고 건수 보고("12행 중 10행 저장, 2행 형식 오류"). 자동 보정 금지.

## 6. FR-LBL 라벨 전이 [변경 D6]

```text
L0 --(actualValue가 있는 granularity=total 실측 최초 저장)--> L1
L1 --(actualValue와 bucketLabel이 있는 hourly/zone 실측 저장)--> L2
L0 --(actualValue와 bucketLabel이 있는 hourly/zone 실측 최초 저장)--> L2   (단계 건너뜀 허용)
역방향 전이 없음. L3 도달 불가(MVP).
```

- 전이는 ACT-07(실측 저장) 내부에서만 발생한다. 다른 경로로 labelLevel을 쓰지 않는다.
- 복제 시 새 축제는 L0으로 리셋(FR-CLONE).

## 7. FR-RPT 보고서 · FR-CLONE 복제 · FR-LOG 호출로그
