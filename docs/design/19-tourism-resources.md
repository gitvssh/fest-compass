# 관광자원 공통 상세와 음식점·숙박

설계일: 2026-09-26. 대상: 기존 축제의 주변 관광자원과 새 축제의 지역 관광자원.
상태: 설계·구현·공개 화면 검증 완료. 사용 가능. 실행 결과는 [기록41](../validation/41-tourism-resources.md)을 따른다.
이후의 관광자원 시각 표현·군집 선택과 목적 이미지는 [설계20](20-resource-experience.md)을 따른다. 아래 데이터·주소 계약은 유지한다.

## 화면 목표

담당자가 고른 축제·지역에서 방문객이 함께 둘러보고, 식사하고, 머물 장소를 조사한다.
장소를 열어 소개와 위치를 확인하고 기준점을 정해 거리를 비교할 수 있다. 장소 선택은 임시이며
기획 의도 입력·저장·자동 추천을 요구하지 않는다. 모든 등록 축제에 동일한 기능을 적용한다.

## 공식 자료 확인

[한국관광공사 국문 관광정보 서비스](https://www.data.go.kr/data/15101578/openapi.do)의
지역 기반 목록 `areaBasedList2`와 공통 소개 `detailCommon2`를 사용한다. 2026-09-26 직접 조회:

| 지역 | 음식점(39) | 숙박(32) |
|---|---:|---:|
| 강남구 | 260 | 32 |
| 제주시 | 426 | 89 |
| 서귀포시 | 272 | 121 |
| 강릉시 | 478 | 178 |
| 논산시 | 28 | 3 |

총 10개 목록의 첫 페이지로 등록 건수·유형·법정동 지역을 확인했다. 제주시·강릉시의 음식점·숙박
각 1곳, 총 4곳에서 상세의 동일 ID·유형·지역과 소개를 확인했다. 표는 해당 시점의 API 등록 건수다.
전국 사업체 수, 영업 중인 시설 수, 객실·수용 인원·예약 가능 수가 아니다. 메뉴·요금·객실 정보는
이번 구조화 항목에 추가하지 않는다. 홈페이지는 확인한 4건 모두 비어 있어 별도 링크 기능을 확대하지 않는다.

## 기본 배치와 행동

```text
지역 관광자원                         지역명
[관광지✓] [문화시설✓] [음식점] [숙박]
기준점이 있을 때: 기준점 / 반경 / 정렬 / 해제
유형별 등록 건수 또는 불러오기 상태
┌ 장소 목록 ────────────┬ 지도 ────────────┐
│ 이름 / 유형 / 주소    │ 동일한 번호       │
│ 기준점이 있으면 거리  │ 좌표 있는 장소    │
└─────────────────────┴─────────────────┘
선택 장소: 이름 / 닫기
유형 · 주소 · 위치 · 기준점 직선거리
[이 장소를 기준점으로]  새 축제: [함께 보기]
소개: 일반 텍스트, 긴 소개는 더 보기
소개 출처                         목록 출처
```

- 초기 선택은 현재와 동일한 관광지·문화시설. 음식점·숙박 버튼을 같은 위계로 노출하고 선택한 유형만 조회한다.
- 유형 순서는 관광지·문화시설·음식점·숙박. 네 유형 모두 끌 수 있고 그때는 짧게 유형 선택을 안내한다.
- PC는 기존 목록·지도 2열, 모바일은 목록/지도 전환을 유지한다. 상세는 선택 뒤 아래에 열리고 제목으로 초점 이동한다.
- 기존 축제에도 새 축제와 같은 소개 블록을 제공한다. 이름·유형·주소·거리·소개·출처의 의미와 정제 규칙은 공통이다.
- 상세 열기·기준점 지정·새 축제의 최대 2곳 함께 보기는 독립 행동이다. 함께 보기는 기존 축제로 확대하지 않는다.
- 소개가 없으면 소개 영역을 생략한다. 실패는 해당 영역의 짧은 상태와 재시도로 표현한다. 목록·지도는 계속 사용한다.
- 실패한 유형이 다른 유형의 목록을 지우거나 기다리게 하지 않는다. 필터로 숨겨진 상세·함께 보기·기준점은 보존한다.
- 좌표가 없으면 목록을 유지하되 지도·반경 안 건수에는 포함하지 않는다. 거리는 직선거리로 표시한다.
- 등록 건수와 자료 출처는 유지하고 내부 호출 한도·정제·일치 검증 절차를 제품 문구로 노출하지 않는다.
- 최종 시각 디자인은 후속 디자인 작업에서 다룬다. 이번에는 기존 스타일과 기본 위계를 사용한다.

## 구현 계약

1. `ResourceKind`는 12/14/39/32, `RESOURCE_KINDS`는 같은 표시 순서. 기본값은 별도
   `DEFAULT_RESOURCE_KINDS = [12,14]`로 둔다. 생략·무효 URL은 기존 기본값을 유지하며 `types=none`은 모두 해제한다.
   네 유형 선택은 `types=12,14,39,32`로 명시한다. 기존 `types=12,14` 링크의 의미는 유지한다.
2. 기존 일회성 `resource=<kind>:<id>`도 네 유형을 받는다. 대상 유형을 한 번 추가하고 성공한 해당 지역 전체 목록에서만
   상세를 연다. 주소·새로고침·뒤로가기·지역/축제 전환의 기존 조건 보존과 선택 해제 규칙을 유지한다.
3. 두 화면은 네 개의 고정 Hook 또는 공통 고정 Hook으로 유형별 요청을 독립 실행한다. 선택 배열에 따라 Hook을 호출하지 않는다.
4. 목록 수집은 페이지당 100건, 최대 20페이지(유형당 2,000건)로 제한한다. 관측 최대 478건보다 여유를 두며
   전체 페이지 수·총수 불변·ID 중복·지역·명시적 유형 일치를 확인한다. 600건 초과만으로 실패하지 않는다.
   2,000건 초과·부분 응답·변동·불일치는 그 유형만 실패 처리하고 일부를 전체인 것처럼 표시하지 않는다.
   축제(15)의 기존 조회 한도와 일정 검증은 보존한다. 공통 호출 빈도·동시성·크기·시간·캐시 제한을 유지한다.
5. 소개는 기존 검증 로더를 공통으로 사용한다. 공통 `/api/resources/detail`을 추가하고 이전 `/api/new/resource-detail`은 호환 유지한다.
   `detailCommon2`에는 `contentId`만 전달한다. 정확한 단일 ID·명시 유형·검증된 지역이 일치해야 소개를 반환한다.
   HTML을 제한 길이의 일반 텍스트로 정제하며 동적 HTML 삽입은 없다. 목록과 소개의 수집 시각을 혼동하지 않는다.
6. 영업·잔여 객실·예약·추천 등 제공하지 않는 정보를 추정하지 않는다. 앱 DB·사용자 데이터·공급자 등록 정보를 변경하지 않는다.

## 완료 기준

- 두 흐름에서 네 유형 선택·목록·지도·거리·소개가 연결되고 특정 축제 전용 조건이 없다.
- 601건 이상 전체 수집, 2,000건 경계, 종류/지역 불일치, 누락·중복·총수 변동은 자동 검증한다.
- 음식점·숙박 상세, 소개 결측·실패·재시도·빠른 선택 전환, 유형 조건 복원, 기존 상세 도착 링크를 headless로 검증한다.
- 320/390/1440px에서 목록·상세·함께 보기·초점과 가로 넘침을 확인한다. 공식 실제 데이터 검증과 통제 시험은 구분한다.
- 전체 기존 필수 검사 후 주 담당자가 직접 검수하고, 공개 배포·실제 화면 확인·D 드라이브 사본 전달까지 기록한다.
