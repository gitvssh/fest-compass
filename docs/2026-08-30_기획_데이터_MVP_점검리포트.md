## 1. 요약 — 지금 막고 있는 것 3가지

| 순위 | 문제 | 영향 | 다음 조치 |
|---|---|---|---|
| 1 | **TOUR_API_KEY가 빈 값** (`apps/web/.env`) | 공모전 기간 내 검증 1번 항목(실키 호출·응답 로그, 개선안 §4.1)이 현재 미충족. 실데이터 검증 전체가 차단됨 | data.go.kr 키 발급 + **6개 API 각각 활용신청** (§2.1 목록) |
| 2 | **수요 강도 API 엔드포인트가 실존하지 않는 경로** (`lib/kto/client.ts`의 `DataLabService/areaTarSjrnDsList`) | 키를 넣어도 이 호출은 항상 실패(400 NO_OPENAPI_SERVICE_ERROR). 실호출로 확인 완료 | `AreaTarDemDsService/areaTarExpDsList`로 교정 (§2.2) |
| 3 | **지역코드 체계 불일치** — KorService2의 `areaCode`(관광공사 자체코드)를 데이터랩 계열 `areaCd`(행정표준 시도코드)에 그대로 전달 (`lib/kto/refresh.ts`) | 방문자·수요강도·집중률 호출이 엉뚱한 지역을 조회하거나 빈 결과. 예: 전북은 KorService 37, 데이터랩 52 | 코드 매핑 테이블 추가, 실키 확보 후 실호출로 확정 (§2.3) |

기획서 자체의 판단 구조(증거등급·라벨 게이트·금지 해석·의사결정 게이트)는 견고하며 문서 작업의 정본으로 쓸 수 있다. 구체화 대상은 §4에 문서별로 정리했다.

## 2. 데이터 실검증 결과 (2026-08-30 실호출)

### 2.1 엔드포인트 실존 검증

키 없이도 게이트웨이 응답으로 경로 실존을 판별할 수 있다
(실존 경로 → HTTP 403 `SERVICE_KEY_IS_NOT_REGISTERED`, 없는 경로 → HTTP 400 `NO_OPENAPI_SERVICE_ERROR`).

| 기획서 §6.2 데이터 | data.go.kr | 실제 엔드포인트 (검증됨) | MVP 구현 | 검증 결과 |
|---|---|---|---|---|
| 국문 관광정보 (축제검색·키워드·상세) | 15101578 | `KorService2/searchFestival2`, `searchKeyword2`, `detailCommon2` | ✅ 구현 | ✅ 경로 실존 |
| 지역별 방문자 수 | 15101972 | `DataLabService/locgoRegnVisitrDDList` (기초) / `metcoRegnVisitrDDList` (광역) | ✅ 기초만 구현 | ✅ 경로 실존 |
| 지역별 관광 수요 강도 | 15151868 | **`AreaTarDemDsService/areaTarExpDsList`** (파라미터: `areaCd`, `signguCd`, `baseYm`) | ❌ **잘못된 경로** (`DataLabService/areaTarSjrnDsList` — 실존하지 않음) | ⚠️ 교정 필요 |
| 지역별 관광 자원 수요 | 15152138 | **`AreaTarResDemService/areaTarSvcDemList`** | ❌ 미구현 | ✅ 경로 실존 |
| 관광지 집중률 | 15128555 | `TatsCnctrRateService/tatsCnctrRatedList` | ✅ 구현 | ✅ 경로 실존 |
| 관광지별 연관 관광지 | 15128560 | `TarRlteTarService1/areaBasedList1` | ❌ 미구현 | ✅ 경로 실존 |

**활용신청 필요 목록**: 위 6개 데이터셋 각각에 대해 data.go.kr에서 활용신청해야 같은 인증키가 통과된다.
개선안 §3 시그니처 사용례의 "분산 동선·연계 프로그램" 결정은 집중률+**연관 관광지**를 쓰는데 연관 관광지가 미구현 —
발표 스토리와 데모의 정합을 위해 구현 또는 스토리 축소 중 택일해야 한다.

### 2.2 수요 강도 엔드포인트 교정 내용

- 현재: `https://apis.data.go.kr/B551011/DataLabService/areaTarSjrnDsList` → 항상 400
- 교정: `https://apis.data.go.kr/B551011/AreaTarDemDsService/areaTarExpDsList`
- 응답 필드명도 현재 파서(`tarSjrnDs` 등)와 다를 가능성이 높으므로 실키 확보 후 응답 스키마를 다시 맞출 것
- `prisma/seed.ts`와 `evidence/page.tsx`의 apiName 문자열(`areaTarSjrnDsList`)도 함께 교체

### 2.3 지역코드 체계

- KorService2 `areaCode`: 관광공사 자체 코드 (서울 1, …, 경기 31, 전북 37, 제주 39)
- 데이터랩 계열 `areaCd`: 행정표준 시도코드 (서울 11, …, 전북 52, 제주 50), `signguCd`: 시군구 5자리
- `refresh.ts`는 `festival.areaCode`를 데이터랩 3개 API에 그대로 전달 → 매핑 테이블 필요
- 시드 데이터의 `areaCode: "36", sigunguCode: "1"`도 두 체계 어느 쪽으로도 좌표(충남권)와 안 맞음 — 데모용이지만 실호출 연결 시 정리 필요

### 2.4 조회 기간 정의 문제 (명세로 확정 필요)

`refresh.ts`는 방문자·수요강도를 **축제 시작일 기간**으로 조회한다. 미래 축제(D-90 시점)에는 해당 기간 데이터가 아직 없다
(데이터랩 데이터는 지연 공개). 기획서 §5.4의 "D-90 지역 배경" 용도라면 **전년 동기간 + 평시 구간**을 조회해야 한다.
어느 기간을 몇 개 구간으로 불러올지(예: 전년 축제주간 ±2주)를 API 명세서에서 확정할 것.

## 3. MVP 점검

### 3.1 기획서 §10.1 "반드시 구현" 대비 현황

| 항목 | 상태 |
|---|---|
| 축제 기본정보 입력 + KTO 실호출 | ✅ (신규등록 화면 + refresh) — 단 실키 없음 |
| 출처·기준일·집계정의 스냅샷 | ✅ EvidenceSnapshot + stale 처리 |
| 최소·기준·최대 가정 | ✅ |
| 유입·체류·수용량 단순 계산 | ✅ `lib/calc/capacity.ts` + 테스트 4건 통과 |
| 세 시나리오 비교 | ✅ (단 §3.2-D 시나리오 축 정의 문제) |
| 선택안·이유·승인자 기록 | ✅ |
| 계획값·실제값 구분 | ✅ Outcome planned/actual |
| 결정·성과 원장 + 보고서 | ✅ |
| API 오류·결측·라벨없음 상태 | ✅ (L0/L1만 — L2/L3 화면 미정의) |
| **실호출 로그·개발계정 증빙** | ❌ **키 부재로 실증빙 없음** |

### 3.2 발견된 기획-구현 불일치·버그

- **A. 안전 권고 비활성 조건 불일치**: 기획서 §6.4·화면 문구는 "기준문서와 승인자가 없으면 안전 자동 권고 비활성"이라 하지만,
  `capacity.ts`의 `safetyEnabled`는 `approvedCapacity > 0`만 확인한다. `documentRef`·`approver` 부재 시에도 수용여유·점유율 경고가 켜진다.
- **B. 수요강도 엔드포인트** (§2.2) / **C. 지역코드** (§2.3) / 조회 기간 (§2.4)
- **D. 시나리오 축이 섞여 있음**: 보수안=유입 최소값(수요 축), 확대안=셔틀·인력 증가(자원 축, 유입은 기준값).
  "보수/기본/확대"가 수요 가정의 축인지 자원 투입의 축인지 기능명세서에서 정의해야 비교표가 성립한다.
- **E. 가정 버전 관리 불완전**: `updateAssumptionsAction`에서 inflow만 version+1, 나머지 항목은 항상 version 1.
- **F. Decision.changeSummary가 셔틀·주차만 요약** — sessions·routeNote 미반영.
- **G. 라벨 전이 규칙 미정**: Outcome 입력 시 L0→L1 자동 전이만 존재. L1→L2(시간·구역 계수 확보) 조건 미구현·미정의.
- **H. D-3 트리거 등록 기능 없음**: 개선안 §2.2 워크스루의 "우천 시 셔틀 증편 트리거 등록"에 해당하는 사전 트리거 객체가 없다
  (FieldAction은 사후 기록만). 데모 스토리에 있으므로 범위 결정 필요.
- **I. e2e 스크립트가 Windows 전용 경로** (`scripts/demo-e2e.mjs`가 `C:/dev/...`의 playwright 참조) — WSL에서 실행 불가.
- §10.2 "가능하면 구현" 중 CSV 업로드·PDF/공유 링크·역할 권한은 미구현 (예정대로면 문제 아님).

## 4. 문서 작업별 구체화 필요 사항

기존 기획서가 이미 정본 역할을 하는 부분: 사용자 여정(§5.4), 모듈 정의(§5.5), 데이터 모델(§5.6), 데이터 계약(§6.2),
라벨 게이트(§6.3), 개선안 §2 워크스루·90초 데모. 아래는 그 위에서 **새로 결정**해야 할 것들이다.

### 4.1 유스케이스 / 사용자 flow

- 액터 정의: 총괄·안전·교통·성과 담당을 유스케이스에서 구분할 것인가? 현재 MVP는 `author` 텍스트 입력뿐.
  로그인 없는 "역할 선택" 수준인지, 실제 계정·권한인지 결정 (§10.2와 연결).
- 시점별 유스케이스는 §5.4 표의 5개 행(D-90/D-30/D-3/행사일/D+14)을 그대로 전개하면 된다.
  단 **D-3 트리거 등록**(§3.2-H)의 포함 여부를 먼저 결정.
- 예외 흐름: 키 없음 / API 오류 / 빈 결과 / stale / 라벨 L0 각각에 대해 "사용자가 다음에 무엇을 하는가"를 flow로 명시
  (§6.4 규칙은 있으나 화면 단위 행동으로는 미전개).
- 복제(다음 행사) flow: 무엇이 이관되고 무엇이 초기화되는지 — 현재 구현: 가정·수용량·시나리오 이관 / 스냅샷·결정·실측·라벨 초기화.
  이 동작을 명세로 확정.

### 4.2 화면설계서

- 라벨 게이트 L0~L3 **상태별 화면 변화 매트릭스** (현재 L0/L1 두 문구만 존재).
- 시나리오 비교표의 컬럼 확정: 피크동시체류·수용여유·점유율·경고상태(85%/100%) + 자원 항목. §3.2-D 축 정의가 선행.
- 각 화면의 빈 상태·오류 상태·stale 표시 규칙 (컴포넌트는 있음: Guardrail, EmptyValue, KindBadge — 사용 규칙을 문서화).
- 4종 데이터(관측값·가정·계산값·실측값) 배지의 색·문구 규칙 (§6.1 표현 규칙의 시각 언어 확정).

### 4.3 기능명세서

- 계산식: `capacity.ts`의 식과 경고 임계(0.85, 1.0)를 명세에 옮기고 **임계값의 근거**(안전관리 매뉴얼 등) 명시.
- 가정 버저닝 규칙 (§3.2-E 해소), 라벨 전이 규칙 (§3.2-G), 안전 권고 활성 조건 (§3.2-A 해소).
- 시나리오 3종의 정의 (§3.2-D).
- 보고서에 포함되는 섹션·수치·역추적 표현(현재 report 페이지의 4개 섹션이 초안).

### 4.4 API 명세서

- **외부(KTO) 데이터 계약**: §6.2 표를 실 엔드포인트·파라미터·응답 필드·갱신 주기·코드 체계로 확장.
  §2.1의 검증된 경로를 반영하고, API별 활용신청 상태를 추적 컬럼으로 관리.
  조회 기간 정의(§2.4)를 여기서 확정.
- **내부 API**: 현재 MVP는 REST 계층 없이 Next.js 서버 액션(`lib/actions.ts`의 10개 액션)으로 구현됨.
  API 명세서를 REST로 쓸 것인지, 서버 액션 명세(액션명·입력 필드·검증 규칙·부수효과)로 쓸 것인지 결정.
  공모전 제출물 요건이 REST API 문서를 요구하는지 공고문 재확인 필요.

### 4.5 데이터 검증 계획 (개선안 §4.1 실행)

키 확보 후 순서: ① 6개 API 정상 호출 → ② 빈결과·오류·한글·페이징 케이스 로그 확보(ApiCallLog에 자동 적재됨) →
③ 지역코드 매핑 확정 → ④ 전년 동기간 조회로 배경선 데이터가 실제로 존재하는지 확인 →
⑤ 실축제 1건(예: 반복 개최 중소형)으로 seed가 아닌 실데이터 워크스페이스 생성.
