# 지역 관광자료에서 올해 축제 기획까지

## 검수 상태와 목적

**문서·화면 시안 검수 가능 / 새 지도·비교·기획 기능은 개발 필요 / 실무자 검증 미실시.**
2026-09-08 사용자는 구현보다 기획·요구사항·기능목록·화면설계·와이어프레임을 먼저 검토하고 traceboard에 게시하도록 요청했다.
이 문서는 그 요청의 전국 진입·실자료·시각화 검토를 반영한 검수 초안 v3이다. 화면 경로와 배치는 제안이며 사용자 검수를 마쳤다고 표시하지 않는다.

[제품 범위](../../product/vision-scope.md), [요구사항·기능목록](../1-analysis/srs.md),
[화면 흐름](../2-design/flows.md), [검수 안내](../../review/2026-09-planning-review.md)를 함께 읽는다.

## 문제와 사용자

관광부서 담당자는 먼저 자기 지자체의 관광자원과 방문 추세를 파악하고,
주변 행사와 과거 기록을 비교한 다음 올해 열 축제의 주제·아이템·장소·시기·규모를 정해야 한다.
자료를 조회해도 어느 판단에 썼는지 남지 않으면 결재 자료와 다음 해 기획을 다시 만들어야 한다.

| 사용자 | 수행할 업무 | 이번 제품의 경계 |
|---|---|---|
| 주 사용자: 시군구 축제 담당자 | 지역 이해, 후보 기획, 예산 설명, 기획안 작성 | 전국에서 담당 지역으로 좁혀 탐색 |
| 협업 대상: 관광재단·대행사·교통/시설 담당자 | 사례·견적·운영 제약 제공 | 초기에는 자료 입력·파일 전달. 공동 편집은 후속 |
| 검토자: 부서장·예산 검토자 | 후보별 근거와 비용·미확인 사항 확인 | 출력 기획안 검토. 시스템의 공식 결재 기능은 제외 |

내 지역 정보가 1차, 주변·과거 비교가 2차라는 순서는 사용자 제시 가설이다.
실제 담당자 인터뷰와 과제 관찰은 아직 없으므로 수요 검증 완료로 주장하지 않는다.

## 초기 기획과의 관계

초기 분석설계 기획서 §5는 공공데이터·가정·대안·변경·결과 연결을 정의했고,
개선안 §3은 일정 중복, 연계 관광, 시기·주제 적합성을 데이터 활용 목적으로 정했다.
이 목적은 유지한다. 기존 MVP의 시작점인 '정해진 축제 등록' 앞에 지역 탐색과 신규 기획 후보 구성을 추가한다.

원문: [초기 제품 정의](../../archive/2026-08-planning/2026_과제9_FEST_Compass_분석설계_기획서.md),
[활용 개선안](../../archive/2026-08-planning/2026_과제9_FEST_Compass_기획서_개선안.md).
기존 문서의 예측 정확도 연구·운영 중심 구현 순서가 이번 제품 우선순위를 대체하지 않는다.

## 최종 산출물: 담당자가 설명할 수 있는 기획안

| 기획안 내용 | 반드시 함께 남길 것 |
|---|---|
| 축제 목적·주제·아이템·대상 방문층 | 지역 특성과 비교 사례, 담당자 판단 |
| 후보 장소·기간과 선택안 | 관광자원·접근 조건·일정 겹침·미확인 사항 |
| 적어도 두 기획 대안 | 선택·제외 이유, 각각에 사용한 근거 |
| 프로그램·시설·인력·교통·홍보 준비 | 수량·단가·단위·금액 출처, 견적과 가정 구분 |
| 재원·지출·예산 단계와 증감 | 확보/예정·미산정, 한도 초과, 전체/부분 범위, 기준 버전·변경 이유 |
| 선택 당시 자료 | 지역·기간·단위·조회 조건·출처·수집일·선택 당시 값 |
| 운영 후 재사용 | 같은 정의의 실측, 재원별 실제 사용·잔액/반납/이자 확인, 문제→조치→차기 준비/예산 |

자동으로 '최적 축제'를 정하는 기능은 약속하지 않는다. 담당자가 후보를 구성하고
근거·제약을 비교해 선택한다. 예측은 검증한 지역과 지표 범위의 보조 정보다.

## MVP 범위와 전달 순서

[M1~M6 제품 마일스톤](../../design/07-region-planning-milestones.md)의 전체 동선을 먼저 설계한다.
D0 기획·설계 검수 후 구현 순서는 M1 → M2 → M3 → M4~M6 연결이다.
논산을 첫 검증 사례로 사용하되 다른 지역 선택 시 자료 부족을 표시한다.
전국 모든 과거 회차를 수집하는 일은 첫 지도 검증의 선행 조건이 아니다.

| 단계 | 이번 설계가 정하는 것 | 개발 때 남은 확인 |
|---|---|---|
| D0 문서·시안 | 요구사항, 자료 정의, 예외 흐름, 7개 핵심 화면, 인수 시나리오 | 담당자 피드백 반영 |
| M1 지역 탐색 | 지역/기간 공통 필터, 지도·목록·차트, 출처와 자료 부족 | 지도 공급자·경계·좌표, 지역별 실제 응답 |
| M2 비교 | 현재 등록 일정·과거 개최회차 검색, 동일 지표 비교 | 축제·회차 식별과 자료 보유 범위 |
| M3 기획 | 사업 정보·수행 관계, 근거 연결, 두 후보·장소 기간·준비 과제 | 후보 입력과 저장 구현 |
| M4 예산·준비 | 재원/지출 분리, 산출 기준·단계·분류, 증감 사유·한도·미산정 | 견적 자료 입력과 계산 구현 |
| M5 기획안 | 근거·대안·재원/비용·준비 상태 보존, 사업설명·준비 목록 출력 | 기획안 스냅샷·인쇄 구현 |
| M6 다음 회차 | 재원별 실제 사용·확인 상태·개선 연결·결과 출력, 과거 기록 재검색 | 기존 개인 작업과 연결 |

## 설계 초안의 기본값

이 값들은 사용성을 검토하기 위한 제안이며 조사로 확인한 사실이 아니다.
최초 화면은 전국지도이며 시도→시군구로 좁힌다. 우리 지역·이전 탐색 이동은 명시적 선택으로 제공한다. 대상 연도는 사용자가 선택한 기획 연도다.
지역 통계 기간과 축제 개최기간은 별도 필터로 표시한다.
비교는 2~3개 개최회차의 가용 지표를 선·막대·구성비 차트로 먼저 읽고 같은 수치 표와 출처로 확인한다.
주변 범위는 지역 선택을 먼저 제공하고 거리 검색은 좌표가 검증된 항목에만 적용한다.
지도를 이동하는 것과 조회 범위를 바꾸는 것은 구분하며 '이 영역 조회'를 눌러야 조건이 바뀐다.
예산은 원 단위로 저장·계산하고 만원 표시 때 원금액을 확인할 수 있게 한다.

## 사용성 검수와 성공 판단

과제: 담당 지역의 올해 기획안 두 개를 만들고 하나를 선택한 이유를 공공데이터로 설명한다.
먼저 시안으로 정보 수요·용어·버튼 위치·화면 연결을 검토한 뒤 구현 후 같은 과제를 관찰한다.
측정 목표 초안은 무도움 15분 내 완주, 각 주요 선택에 출처 추적 가능, 지역 방문자와 입장 건수 혼동 0건이다.
15분은 달성 실적이 아니다. 자료가 없는 지역으로 전환하고 저장 후 재진입하는 과제도 포함한다.
[검수·인수 전략](../3-testing/acceptance-plan.md)에 실행 여부를 구분한다.

## 문서의 기준과 변경

요구사항 ID는 SRS, 화면 ID는 화면설계서가 소유한다. 기능목록을 별도 중복 대장으로 만들지 않는다.
기존 FR·UC·SCR ID는 재번호하지 않으며 기존 설계는 당시 운영 기능의 상세 근거로 보존한다.
accepted ADR은 수정하지 않는다. 저장·권한 경계 변경이 필요하면 별도 후속 결정을 남긴다.

## 공개 사례 반영의 의미

[8개 보완안](../../research/2026-09-municipal-requirement-proposals.md)을 문서·인수 기준·화면 v2에 반영했다. 사업 정보는 지도 탐색 이후 필요한 단계에서 입력한다. 목적별 출력은 기관 서식에 옮겨 쓸 검토 자료이며 공식 예산 편성·계약·지급·정산 승인 기능은 아니다. 실무자의 실제 과제 관찰은 남아 있다.

## 전국·시각화 보완 v3

사용자가 승인한 시작점은 전국지도→시도→시군구다. 자기 지역 정보가 첫 업무 수요라는 목표와 첫 지도 범위를 구분한다.
[시각화 설계](../2-design/data-visualization.md)에 차트 종류·비교 가능 조건·출처·선택 구간 저장을 정의했다.
가상 방문 곡선 대신 논산 실제 과거 표본을 사용한다. 전국 자료 완비는 가정하지 않으며 자료가 없는 곳은 미확보로 표시한다.
