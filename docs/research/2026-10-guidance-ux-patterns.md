# 단계 안내·체크리스트·화면 이미지 UX 조사

- 작성일: 2026-10-03. 외부 자료는 이 날짜에 열람했다.
- 대상: pickDday의 두 흐름(기존 축제 개선 / 새 축제 기획)과 선택형 기획 도구. [설계24](../design/24-planning-guide.md)의 근거다.
- 성격: 외부 패턴·근거 조사와 적용 시사점. 디자인 확정안이나 구현 지시가 아니다.
- 작성: 조사 보조 에이전트가 수집·정리했고, 주 담당자가 설계 반영 전 핵심 규칙(GOV.UK step by step·task list 사용 조건, USWDS 단계 표시기의 비선형 금지, KRDS 도움 패널·코치마크 규칙)을 원문 화면에서 확인했다.
- 표기: [G1], [K3] 같은 표시는 8장 출처 목록의 ID다. 근거 등급(A~D)과 '(추론)' 표시는 1장에서 설명한다.
- 제품 제약 약칭(9장도 동일)
  - C1 데이터는 알려주되 결정하지 않는다(자동 "최적 날짜·주제" 금지).
  - C2 기록·답변은 선택이다. 탐색은 폼·체크리스트 없이 가능해야 하고, 체크리스트는 이동을 막을 수 없다.
  - C3 내부 절차·검증 규칙은 화면 문구로 노출하지 않는다. 사용자에게 필요한 정보만 쓴다.
  - C4 PC 우선이되 좁은 폭·200% 확대·키보드 조작을 지킨다(WCAG 2.1 AA).
  - C5 선택 상태는 브라우저(localStorage)에만 두고 로그인은 없다.

## 0. 한눈에 보기

1. **정부 "단계" 패턴은 절차(신청·제출)용이다.** GOV.UK는 step by step navigation을 "읽기만 하는 안내"나 "논리적·유용한 순서가 없는 경우"에 쓰지 말라고 하고 [G1], 작업 목록(task list)에는 "모든 과업이 Completed일 때만 다음으로 진행"이라는 거래용 규칙이 있다 [G2]. USWDS는 비선형 흐름에 단계 표시기를 쓰지 말라고 한다 [U1]. pickDday의 탐색은 NN/g가 말하는 '폼'이 아니라 순서 없이 오가는 '애플리케이션'에 가깝다 [N17]. 가져올 것은 내용 설계(목표, 할 일 묶음, and/or, 선택 표시, 비용·시간)이고, 흐름 통제(비활성 단계, 완료 요구, 제출 전 확인)는 가져오지 않는다.
2. **KRDS는 공무원에게 익숙한 도움 어휘를 구체 규격으로 갖고 있다.** 도움 패널, 따라하기 패널, 맥락적 도움말, 코치마크(자동 실행 금지·4개 이하), 툴팁(150자 내외) [K4~K9]. 반면 컴포넌트 목록 [K1]과 디자인 스타일 목록 [K20]에는 체크리스트·작업 목록·프로세스 목록·일러스트 지침이 없다. 개념은 GOV.UK·USWDS에서 빌리고 KRDS 규칙(필수 정보는 본문, 자동 실행 금지, 44px 등)으로 감싸는 구성이 현실적이다.
3. **초심자 지원에서 근거가 가장 단단한 것은 '지금 하는 일에 붙은 짧은 안내(pull)'와 '읽는 법을 보여주는 예시'이고, 시작 시 튜토리얼은 약하다.** NN/g의 70명 시험에서 튜토리얼을 읽은 그룹과 건너뛴 그룹의 과업 성공률은 91% 대 94%(유의차 없음)였고, 읽은 쪽이 과업을 더 어렵게 평가했다 [N19](모바일 앱 대상이라 전이는 제한적). 예시와 단계 안내는 초심자에게 효과적이지만 숙련자에게는 중복·역효과가 된다(expertise reversal) [L1].
4. **체크리스트는 이번 요청에서 가장 조심할 항목이다.** 'Checklist for Checklists' 문서 자체가 "A checklist is NOT a teaching tool or an algorithm"이라고 적고, 항목을 '누락 위험이 큰 핵심 단계'로 한정하며 pause point당 10개 미만을 권한다 [C1]. 길어지면 단축·습관화된 응답이 나타나고 [C2], 의무화·형식화되면 tick-box 인식과 준수 저하가 생긴다 [C6][C7]. 데이터 탐색 화면에는 '살펴볼 질문'(체크 상태 없는 문장)을, 기획 도구에는 선택형 점검 목록을 두는 쪽이 안전하다.
5. **비선형 탐색 + 권장 순서:** 탭은 번호·잠금 없이 유지하고 순서는 탭 바깥(개요 스트립, 패널 끝의 '이어서 살펴볼 화면' 링크)에서만 알린다. 진행은 '방문함'(자동, 중립)과 '살펴봤어요'(사용자 표시, 선택)를 분리하고 퍼센트·막대·'완료' 어휘를 쓰지 않는다.
6. **이미지:** 정보를 싣지 않는 장식 이미지는 시선에서 무시되고 [N14] 이해를 소폭 해친다(seductive details 메타분석 기준 작은~중간 효과) [L3][L4]. 정보 시각화, 프로세스 도식, 행동이 이어지는 빈 화면 일러스트는 근거 있는 용도다 [N7][D5]. "모든 페이지에 이미지"는 "모든 페이지에 목적 있는 시각 요소"로 번역하는 편이 안전하다. 홈의 큰 일러스트(사용자 호평)는 길찾기·정체성 기능이므로 유지하되 하위 데이터 화면으로 복제하지 않는다.
7. **'추천'과 기본값은 강하게 작동한다.** 의사결정 지원이 불완전할 때의 자동화 편향은 초심자·전문가 모두에게 나타나고 훈련·지시로 막을 수 없다고 보고되며 [C9], 기본값 효과는 메타분석에서 d=0.68이고 '선택 설계자의 의견'으로 읽힐 때 더 강하다 [C10]. "처음이라면 이 순서"(절차)와 "이 시기가 좋다"(내용)를 분리하고, 정렬·기본 선택·강조가 후자처럼 읽히지 않게 한다.
8. **확인하지 못한 것:** 읽을거리 목록·목표 헤더·권장 순서 표시가 성과를 높인다는 직접 증거는 이번 조사에서 찾지 못했다. 소규모 형성평가가 필요하다(7장).

## 1. 조사 방법과 읽는 법

- **도구:** WebSearch / WebFetch. 웹 페이지는 요약 모델을 거친 결과이고, PDF는 로컬에서 텍스트를 추출해 직접 확인했다(Checklist for Checklists, NASA CR-177549, Boeing Technical Journal, NSW CESE 보고서, Parasuraman & Manzey 2010, González 외 2019). 추출한 텍스트는 조사 작업 공간에만 두고 저장소에는 옮기지 않았다.
- **열람 방식(8장 표기):** 직접(웹 페이지 열람, 요약 모델 경유) / PDF추출(원문 텍스트 확인) / 스니펫(검색 결과 요약만) / 실패(열람 불가).
- **인용:** 요약 모델을 거친 문구는 핵심 규칙 수준에서만 따옴표로 인용했고, 한국어로 따옴표를 친 문구는 영어 원문을 옮긴 번역(일부 의역)이다. 영어로 적은 문구만 원문 그대로다. 설계에 직접 영향을 주는 규칙(KRDS 탭·단계 표시기·코치마크·도움 패널·도움 패턴, GOV.UK 단계·작업 목록의 원문 markdown, CHR&R 시작점 문장)은 두 번 열람해 대조했다. 그래도 산출물에 인용하기 전에 원문 재확인을 권한다.
- **근거 등급:**
  - A: 동료심사 논문·메타분석·정부/기관 연구보고서(초록 또는 본문 직접 확인)
  - B: 정부·기관 디자인 시스템 지침(공식 페이지 직접 확인)
  - C: 실무 연구기관(NN/g 등) 기사·자체 시험
  - D: 2차 요약·블로그·커뮤니티 번역(보조 근거)
  - '(추론)': 출처가 직접 말하지 않고 조사자가 적용 판단으로 덧붙인 내용
- **전이 한계:** 체크리스트·인지부하 연구는 항공·의료·교실 맥락이고, NN/g 튜토리얼 시험은 모바일 앱이다. 지자체 담당자용 데이터 탐색 도구(pickDday)로의 전이는 추론이다.
- **제품 맥락 확인:** 라이브 홈과 /new, /existing을 1회 요약 열람하고 [X2] 저장소 문서(planning-principles.md, functional-spec.md, design-system.md)를 읽었다.
  - 홈 제목은 "어떤 축제를 준비하시나요?", 큰 일러스트 카드 2장, 메뉴(기존 축제, 새 축제, 관광지도, 축제 비교), 기획 도구 6종(담은 근거, 기획 후보, 예산·준비, 기획안·출력, 비용·결과, 내 작업공간), 세 번째 진입 "내 축제 작업 시작"이 있다.
  - 여정 시작 화면에는 이미 "차례와 상관없이 볼 수 있어요"(기존 축제), 지역을 고르면 관광자원·방문 흐름·개최 시기 달력을 살펴볼 수 있다는 안내(새 축제)가 있다.
  - 팀 문서는 세 화면 이동을 "번호가 있는 작성 단계 대신 자유 이동"으로 정했고, 핵심 질문은 "설문·입력 체크리스트가 아니다"라고 정했다.
  - 화면의 실제 시각 위계·alt 텍스트는 요약 열람이라 확인하지 못했다.

## 2. 정부 디자인 시스템의 다단계 안내 패턴

### 2.1 패턴별 적합성과 오용 신호

| 패턴 | 하는 일 | 알맞은 경우(출처 요지) | 오용 신호 | pickDday 판정 |
|---|---|---|---|---|
| GOV.UK Step by step navigation [G1][G11][G12][G13] | 끝에서 끝까지의 여정을 번호 있는 단계로 보여주고, 단계마다 도움이 되는 안내·거래 링크를 묶는다. 사이드바 또는 독립 페이지. | 시작과 끝이 있고, 여러 안내·거래를 거치며, 정해진 순서로 하는 것이 도움이 될 때 | 사용자가 읽기만 할 때, 논리적·유용한 순서가 없을 때, 자료 대부분이 서비스 밖에 있을 때, 거래 서비스 내부(이때는 Complete multiple tasks) | 개념(목표, 할 일 묶음, and/or, 비용 표기)만 차용. 번호 흐름은 부적합 |
| GOV.UK Task list / Complete multiple tasks [G2][G3] | 한 번에 끝낼 수 없는 긴 거래를 과업 목록과 상태로 보여준다. 과업 순서는 자유. | 여러 세션이 필요하고 순서 선택이 필요하다는 증거가 있을 때 | 정해진 순서가 필요한 서비스, 사용자 답변 표시(→ Summary list), "모든 과업이 Completed여야 다음으로 진행" 규칙을 탐색에 그대로 적용 | 기획 도구 허브에만 변형 적용(상태 최소화, 잠금·완료 요구 제거) |
| GOV.UK Check answers + Summary list [G4][G10] | 제출 직전에 입력을 확인·수정하게 한다. 건너뛴 선택 질문은 "Not provided"로 표시. | 소·중규모 거래의 제출 직전, 큰 거래는 섹션 끝 | 제출·확정이 없는 곳, 탐색 중간 관문, 선택 입력을 '빠짐'으로 표시 | 기획안·출력에서 읽기 전용 미리보기(Summary list 형태)만 차용. '확정' 문구 금지 |
| GOV.UK Start using a service [G8] | 서비스가 무엇인지, 내 필요에 맞는지, 필요한 것·비용·시간을 보여준다. | 서비스의 진입점 | 시작점에 복잡한 자격 질문 넣기(서비스 안으로 옮김) | 여정 시작 화면의 내용 구성 기준으로 적합. 별도 관문 페이지로 만들지 않음 |
| GOV.UK Pagination (content sequence) [G9] | 이웃 페이지로 가는 이전/다음 링크에 대상 이름 라벨을 붙인다. | 콘텐츠 순서가 있을 때 | 폼 같은 선형 여정(→ Continue 버튼) | 패널 끝 "이어서 살펴볼 화면" 링크에 적합 |
| GOV.UK Tabs / Details / Accordion [G5][G6][G7] | 콘텐츠를 나누고 숨긴다. | Tabs: 첫 섹션이 대부분에게 가장 중요하고 한 번에 한 섹션만 필요할 때 | 순차 읽기, 탭 간 비교, 대다수가 필요한 정보 숨기기("모두가 알아채지는 못한다") | 3개 뷰 탭은 적합하되 비교 필요에 대한 보완 필요. 접이식은 부가 정보에만 |
| USWDS Step indicator [U1] | 여러 쪽에 걸친 폼의 진행 위치를 보여준다. | 선형 흐름, 3개 이상 단계, back/next 보완용 | 비선형·조건부·3개 미만 단계, 자체 내비게이션으로 사용 | 부적합(탭에 쓰면 폼으로 오인) |
| USWDS Process list [U2] | 고수준 순차 단계를 정적 목록으로 설명한다(3~10단계). | 정적 안내, 단계별 설명 | 멀티페이지 폼(→ step indicator), 비순차 콘텐츠(→ 일반·아이콘 목록) | '권장 순서' 개요 스트립의 정적 표현으로 조건부 적합. 번호는 권장 의미일 때만 |
| KRDS 단계 표시기 [K2] | 서비스 이용 단계와 진행 상태를 시각화한다(3~7단계). | 순차적 탐색과 적응형 탐색(특정 단계를 건너뛰고 다른 단계 먼저) 모두 정의됨. 선택 단계는 마지막에 두고 '건너뛰기' 제공 | 순차적 탐색 모델은 미완료 단계 UI를 비활성화함 | 개념만 참고. 번호 진행 표시는 부적합. 기획 도구에 다단계 작성이 생길 때 후보 |
| KRDS 탭 [K3] | 상호배타적 콘텐츠 섹션을 전환한다. | 첫 섹션이 대부분에게 가장 중요, 한 번에 둘 이상 볼 필요 없음, 빠른 전환 | 탭 간 비교가 필요한 경우, 이해에 순서가 중요한 경우(→ 단계 마법사), 6개 초과 시 인지 부담 경고, '사용 불가' 상태 | 사용 가능. 비교 필요(방문 흐름 대 시기)에 근접하므로 보완 필요 |

### 2.2 GOV.UK에서 확인한 사실

- **Step by step navigation [G1][G11][G12][G13]**
  - 정의: "끝에서 끝까지의 여정을 논리적 단계로 보여주고, 각 단계를 마치는 데 도움이 되는 콘텐츠 링크를 둔다." 구성은 소개, 번호 있는 단계, 단계 안의 과업이다. 과업은 사용자가 해야 하는 순서로 나열하고, 동시에 하는 일은 "and", 선택지는 "or"로 연결하며, 비용은 링크 텍스트 뒤에 붙인다.
  - 사용 조건(원문 markdown 대조): 시작과 끝이 있고, 여러 안내·거래를 거치며, 정해진 순서로 하는 것이 도움이 되는 여정. 쓰지 말 경우: 자료 대부분이 GOV.UK 밖에 있을 때, "사용자가 안내를 읽기만 하고 행동하지 않을 때", "과업을 마치는 논리적·유용한 순서가 없을 때", 거래 서비스 내부.
  - 연구: 사용자 시험 8라운드(장애인, 낮은 디지털 활용 능력 포함)와 Digital Accessibility Centre 검토. 알려진 문제는 "사용자가 단계 내비게이션 머리글을 거의 쓰지 않는다(목적이 불분명할 수 있음)"와 "여러 step by step 사이를 오가며 좌절한다"이다.
  - 성과(GDS 보고, 독립 검증 아님): 과업 완료 성공과 GOV.UK 이용 자신감이 의미 있게 증가했고, 'Learn to drive a car'는 첫 6개월에 124만 회 이용됐다. 6개월 안에 15개 이상 부처와 25개 여정을 발행했고 2019년 2월에는 36개였다 [G12].
  - 실제 구조(콘텐츠 API로 확인): 'Learn to drive a car: step by step'은 단계 7항목(Check you're allowed to drive / Get a provisional licence / Driving lessons and practice / Prepare for your theory test / Book and manage your theory test / Book and manage your driving test / When you pass), 4번째 항목만 "and" 논리, 'optional' 플래그 없음, 링크에 비용 필드(£34~£43, £23, £62~£75) [G13]. 단계 열기·닫기 컨트롤은 JavaScript가 붙이는 요소라 내가 받은 HTML에서는 확인하지 못했다.
  - 구현 메모: 열어 둔 단계를 `sessionStorage`에 기억한다. JS가 꺼지면 모든 단계가 펼쳐진 상태여야 한다 [G11].
- **Task list / Complete multiple tasks [G2][G3]**
  - "과업은 원하는 순서로 완료할 수 있어야 한다." 그러나 "과업이 모두 Completed로 표시될 때만 목록에서 다음 단계로 갈 수 있다"(원문 markdown 대조). 순서가 정해진 긴 서비스에는 쓰지 말고 '저장 후 이어하기'를 쓰라고 한다.
  - 상태: Completed(검정 텍스트), Incomplete/Not yet started(파랑), In progress(청록), Cannot start yet(회색, 링크 없음), There is a problem(빨강). "더 추가할수록 사용자가 기억하기 어렵다. 최소로 시작하고 연구가 정당화할 때만 늘려라."
  - 완료 표시는 라디오 "이 섹션을 완료했나요? 예 / 아니요, 나중에 하겠습니다"로 사용자가 직접 선언할 수 있다. 과업 이름은 동사형, 힌트는 짧은 한 문장. 사용자가 상태를 버튼처럼 누르려 해서 행 전체를 링크로 바꿨고, 우발 클릭·상태 대비·문구는 추가 시험이 필요하다고 밝힌다 [G2].
- **Check answers [G4]:** 제출 직전에 확인 페이지를 두면 "완료했다는 확신이 높아지고" 오류를 한 번 더 고칠 기회가 생긴다. "확인하기 전에는 거래가 끝나지 않는다는 점을 분명히" 해야 한다. 건너뛴 선택 질문은 "Not provided", 수정 후에는 확인 페이지로 곧장 돌아온다.
- **Tabs [G5]:** "탭은 내용을 숨기므로 모두가 알아채지는 못한다." 탭 간 비교는 "정보를 외워 앞뒤로 전환해야 해 답답"하다. 이 컴포넌트는 (조사 시점에) 사용자 연구를 거치지 않았다고 명시한다. 2024년 8월에 스크린 리더 문제로 방향키 바인딩을 제거했다.
- **Details / Accordion [G6][G7]:** 대다수가 필요로 하는 정보를 숨기지 말 것. 일부 사용자는 '더 보기' 링크가 페이지를 벗어나게 할 것이라 생각해 누르지 않는다. 아코디언은 먼저 아코디언 없이 콘텐츠를 시험하라고 권한다.
- **Start using a service [G8]:** 시작점은 "서비스가 무엇을 하는지, 내 필요에 맞는지 알 만큼만" 설명하고, 필요한 것·비용·시간을 알려 준다. 복잡한 자격 정보는 시작점이 아니라 서비스 안에서 묻는다.

### 2.3 USWDS에서 확인한 사실 [U1][U2]

- Step indicator: 여러 쪽에 걸친 폼이 3개 이상 큰 단계로 나뉠 때, "표준 back/next 내비게이션을 보완하는 용도이지 자체 내비게이션이 아니다". "비선형 폼이나 어떤 순서로도 끝낼 수 있는 상호작용에는 적절하지 않다." 3개 미만이면 쓰지 않는다. 접근성: 순서 있는 목록, 완료 여부는 시각적으로 숨긴 텍스트, 현재 단계에 `aria-current`.
- Process list: 고수준 순차 단계를 정적으로 설명하는 용도(3~10단계, 번호는 생략 가능). 현재 상태 추적은 step indicator, 비순차 콘텐츠는 일반·아이콘 목록을 쓰라고 한다. WCAG 2.1 AA 시험에서 2개 통과, 4개 조건부 통과로 표기됐다.

### 2.4 KRDS가 구체적으로 제공하는 것

KRDS 사이트 메뉴는 디자인 스타일 / 컴포넌트 / 기본 패턴 11종 / 서비스 패턴 5종(방문·검색·로그인·신청·정책 정보 확인) 구성이고, 서비스 패턴은 필수(Do)·권장(Better)·우수(Best) 3수준으로 안내한다 [K1][K17][K18][K19]. 컴포넌트 중 이번 주제와 관련된 항목은 다음과 같다. (※ '요약'으로 표시한 행은 1회 열람이므로 인용 전 재확인을 권한다.)

| 컴포넌트(분류) | 핵심 규칙 | pickDday 용도 |
|---|---|---|
| 단계 표시기(피드백) [K2] | 3~7단계, 순차적/적응형 탐색, 선택 단계는 필수 단계 뒤 마지막에 두고 '건너뛰기'·'다음에 입력하기' 같은 명확한 레이블, `<ol>`·색 이외 구분·`aria-current` | 기획 도구에 다단계 작성이 생길 때만 |

### 2.5 오용하기 쉬운 지점(사전 점검)

1. 탭 3개를 번호 단계로 바꿔 "폼"처럼 보이게 하기(USWDS: 비선형에는 부적합 [U1]).
2. 작업 목록의 'Cannot start yet'·비활성 상태를 탐색에 쓰기(KRDS 탭은 '사용 불가' 금지 [K3], KRDS 단계 표시기의 '순차적 탐색'은 미완료 단계 UI를 비활성화 [K2]).
3. 해석에 필요한 정보를 도움 패널·툴팁·접이식에만 두기(KRDS [K5][K7], NN/g [N9], GOV.UK [G6][G7]).
4. 코치마크·투어를 페이지 로드 때 자동 실행하기 [K8][N5].
5. 제출이 없는 곳에 Check answers식 '확인·확정' 단계 넣기 [G4].
6. 시작 화면에 자격·유의사항 질문을 길게 넣기 [G8].
7. 단계 수가 3개 미만인데 step indicator 쓰기 [U1].

### 2.6 시스템 간 충돌과 해석

- **도움 패널의 초기 상태:** KRDS는 도움 패널을 "화면이 로딩되었을 때 열린 상태로" 제공해 존재를 알리라고 하지만 [K5], 코치마크는 자동 실행을 금지한다 [K8]. NN/g는 맥락 없는 push 안내는 건너뛰고 쉽게 닫고 다시 찾을 수 있어야 한다고 한다 [N5]. (추론) 해석: 도움 패널은 '최초 방문에만 열림 → 닫으면 기억 → '?'로 재호출', 코치마크는 사용자가 버튼을 눌렀을 때만.
- **탭 키보드:** KRDS는 Tab/Shift+Tab과 Enter만 규정한다 [K3]. ARIA APG는 방향키 이동을 권장하고 [A9], GOV.UK는 2024-08에 방향키 바인딩을 제거했다 [G5]. (추론) 실제 보조기술(스크린 리더) 조합으로 시험하고 결정할 사항이다.
- **단계 표시기의 선형성:** KRDS는 '적응형 탐색'을 정의하면서도 단계를 "선형적으로 표현"하라고 한다 [K2]. 선형 표현 자체가 '순서'를 강하게 전달하므로 pickDday처럼 순서가 권장일 뿐인 곳에서는 약한 표현(개요 스트립·다음 링크)이 맞다(추론).
- **비활성 상태:** Atlassian 진행 추적기의 disabled는 "다시 방문할 수 없는 단계" 표시 [D4], KRDS 탭은 '사용 불가' 상태를 쓰지 않는다 [K3]. 어느 쪽이든 pickDday에서는 쓰지 않는다(C2).

## 3. 복잡한 전문가 도구에서 초심자를 돕는 패턴과 근거

패턴마다 무엇인지 / 근거 / 함정 / pickDday 번역 순서로 정리한다. 적용 제안의 최종형은 9장에 있다.

### 3.1 맥락적 도움(도움 패널·툴팁·코치마크)

- **무엇:** 사용자가 작업하는 자리에서, 필요하다는 신호(아이콘 클릭, 기능 사용 시작)가 있을 때 짧게 보여주는 안내. NN/g는 맥락 없이 밀어 넣는 push 안내와 신호에 따라 나오는 pull 안내를 구분하고 pull을 권한다 [N5][N10].
- **근거**
  - NN/g 기사: push 안내는 "그 순간 필요한지 모르는 채" 보게 돼 건너뛰게 되고, 기본 정보를 본 사용자는 이후 도움도 가치가 낮다고 보고 건너뛴다. 닫기 쉽고 다시 찾기 쉬워야 한다 [N5][N10]. 다만 이 기사는 "튜토리얼이 과업 수행을 개선하지 않는다"는 문장에 구체 연구를 인용하지 않는다. 새로운 상호작용 방식(AR 등)에서는 워크스루가 유용했다는 예외도 적는다 [N5].
  - NN/g 시험 [N19]: 70명(그룹당 35), iOS 앱 4종, 카드형 튜토리얼 읽기 대 건너뛰기. 과업 성공률 91% 대 94%(유의차 없음), 평균 소요시간 93.5초 대 85.2초(유의차 없음, 튜토리얼 읽는 시간 제외), 난이도 평가(7점) 4.92 대 5.49로 읽은 쪽이 더 어렵다고 평가. 권고는 "UI를 쉽게 만들어 튜토리얼 필요를 줄이고 맥락 도움을 탐색하라"이다.
  - 코치마크·오버레이: 모바일 오버레이는 불필요한 경우가 많고, 한 상호작용에 집중하고 한 번에 하나씩 맥락에서 짧게 보여주며 실제 UI와 구분되게 하라고 한다. 팁을 여러 개 연달아 보여주면 더 빨리 무시한다 [N3].
  - KRDS: 도움을 고정형·사용자 요청형·반응형으로 나누고, 신규·초보 사용자와 복잡한 서비스에는 요청형(툴팁, 맥락적 도움말, 도움 패널, 코치마크, 따라하기 패널)이 적합하다고 규정한다 [K4]. 코치마크는 사용자 요청 시에만, 한 페이지 4개 이하 [K8].
- **함정:** 필수 정보를 도움에만 두기 [K5][K7][N9]. 로드 시 자동 오버레이 [K8]. 우측 레일·배너형이면 광고로 인식되어 무시(3.9) [N4].
- **번역:** 9장 F6, F7.

### 3.2 목표 우선 안내("이 화면에서 무엇을 하는가" 헤더)

- **무엇:** 화면이 시작하는 자리에서 목적·보게 될 것·읽는 법을 먼저 말하는 짧은 블록.
- **근거(패턴 사례 중심. 헤더 자체의 효과를 시험한 연구는 찾지 못했다)**
  - GOV.UK 시작 페이지: 서비스가 무엇을 하는지, 내 필요에 맞는지 알 만큼만 설명하고 필요한 것·비용·시간을 알린다 [G8].
  - GOV.UK Service Manual 단계 안내 페이지: 소제목이 "소요 기간 / 목표 설정 / 문제 정의 / 무엇을 알아낼지 / 공유 / 필요한 팀 / 끝났는지 아는 방법"이고, "정해진 기간은 없고 보통 4~8주", "이 단계에서 멈추는 것은 실패가 아니다"처럼 선택성을 문장으로 밝힌다 [G15].
  - Community Tool Box(CHR&R Take Action Cycle): 섹션이 What / Why / When / Who / How 5개 질문으로 열리고, 체크리스트·예시·도구·슬라이드는 별도 페이지로 둔다 [E1].
  - US Digital Services Playbook: 각 play가 도입 서사 + Checklist + Key Questions이며 "지침이지 의무가 아니다" [D8].
  - NSW Event Starter Guide: 'Before you begin'이 질문 11개(목적, 장소, 대상, 홍보, 승인, 문서, 인력·안전, 예산, 경쟁 행사, 시기, 지역 관광 연계) 형태 [E2].
  - KRDS: 안내 영역은 본문 상단, 화면당 하나, 필수 정보는 인라인 텍스트 [K4].
  - 읽기 행동: 평균 웹 페이지에서 단어의 최대 28%, 현실적으로 20% 정도를 읽고, 절반을 읽는 것은 111단어 이하 페이지뿐이었다(25명, 45,237 페이지뷰, 참가자가 평균 이상의 지능을 가진 대학 직원 등으로 편향, 단어 수 기준이라 한국어로의 환산은 미검증) [N8].
- **함정:** 장문. 결론을 암시하는 문장. '체크해야 하는 질문'으로의 변질(팀 문서가 이미 "핵심 질문은 설문·입력 체크리스트가 아니다"라고 정함).
- **번역:** 9장 F1, F4.

### 3.3 점진적 공개(progressive disclosure)

- NN/g: 자주 필요한 것은 처음부터 보이고, 공개 단계는 2단계를 넘기면 사용성이 낮아지며, 펼치는 버튼은 정보 향기가 강해야 한다. 초심자와 숙련자 모두에게 이득이 있지만 사용자 시험 없이 숨기면 기능을 놓친다 [N1].
- GOV.UK: 대다수가 필요한 정보를 숨기지 말 것 [G6][G7]. 탭도 "숨겨진 내용을 모두가 알아채지는 못한다" [G5].
- KRDS: 디스클로저는 탭·아코디언보다 눈에 덜 띄어 부가 정보에 적합하고, 중요 정보·오류 메시지에는 쓰지 않는다 [K11].
- 번역: 출처·산식·상세 표 같은 보조는 접되, 대상·기간·단위 같은 해석 필수 정보는 항상 보이게 한다(팀 문서의 "수치 해석에 필요한 대상·기간·단위는 읽을 수 있는 지표 표기로 제공"과 같은 방향).

### 3.4 체크리스트 — READ-DO와 DO-CONFIRM, 그리고 한계

**유형 구분**

| 구분 | READ-DO | DO-CONFIRM |
|---|---|---|
| 방식 | 읽으면서 수행한다(레시피처럼) | 각자 기억·경험으로 먼저 수행한 뒤 pause point에서 멈춰 빠진 것이 없는지 확인한다 |
| 알맞은 상황 | 길고 복잡하거나 드물게 하는 과업, 기억에 의존할 수 없는 위급 상황 [C3][C5] | 단계가 잘 알려져 반복되는 과업, 변이가 큰 환경에서 수행 자율성을 지켜야 할 때 [C5][C8] |
| 위험 | 숙련자에게 번거로움, "지능을 모욕한다"는 반응 [C4] | 기억에 의존한 누락, 확인의 형식화 [C2] |
| pickDday 해당성 | 거의 없음(절차 수행 도구가 아니다) | 기획 도구의 '준비 점검'에 한정(추론) |

- 출처 메모: READ-DO를 "읽고 수행(read-and-do)하는, 기억에 의존하지 않는 체크리스트"로 정의한 것은 Boeing Technical Journal 논문(Higgins & Boorman) [C3], 두 유형의 설명은 임상 설계 논문 [C5]. Gawande가 세계 각지 수술 환경에서 "주로 DO-CONFIRM 형식을 택해 유연성을 주었다"고 한 문장은 블로그가 책을 인용한 2차 자료다 [C8](등급 D, 책 원문 미열람).
- Boeing 논문은 체크리스트 범주를 절차(procedural), 준비(preparation), 문제 해결(problem-solving), 예방(prevention)으로 나눈다. 준비형은 "여러 단계의 상황에서 모든 변수가 의도대로 수행되도록 하는" 목록으로 쇼핑 목록·장거리 여행·백패킹 계획을 예로 든다 [C3]. 즉 '계획 준비 목록'은 정당한 체크리스트 범주지만, 근거 연구의 중심은 고위험 절차(예방형)다.

**설계 규칙 — 'Checklist for Checklists' [C1]**

- 목표가 분명하고 간결해야 한다. 각 항목은 "핵심 단계이면서 누락될 위험이 크고", "다른 수단으로 충분히 점검되지 않으며", 구체적인 응답이 있는 행동이어야 한다.
- 작업 흐름의 자연스러운 pause point에서 쓰고, pause point당 10개 미만, 한 쪽에 들어가며, 쉬운 문장과 읽기 쉬운 글꼴, 색 최소화.
- 현장 사용자와 실제·모의 상황에서 시험하고 반복 수정하며, 작업 흐름에 맞고, 오류를 고칠 수 있는 시점에 발견하고, 짧은 시간에 끝낼 수 있어야 한다. 개정 계획과 개정일을 둔다.
- **문서 말미의 주의:** "A checklist is NOT a teaching tool or an algorithm." (저자 표기는 PDF 본문에 없다. 통상 Gawande의 『The Checklist Manifesto』 부록으로 알려져 있으나 이번 조사에서 귀속을 확인하지 못했다.)

**피로·형식화에 대한 근거**

- 항공 현장 연구(NASA CR-177549): 체크리스트가 길면 여러 항목을 묶어 답하거나 읽으면서 바로 수행해 중복 확인(redundancy)을 잃고, 반복되면 "sing-song"이 되어 실제 상태가 아니라 기억으로 답한다. 반대로 너무 짧으면 외워서 건너뛰게 된다. 사용자가 체크리스트를 "귀찮은 일"이 아니라 중요한 것으로 인식해야 한다는 점도 적는다 [C2].
- 질적 연구(캐나다 병원 의료진 31명): "생명을 구한다고는 하지만 정말 그런지 모르겠다"는 tick-box 인식, 사후 보고(debrief) 단계 준수 15~40%, 시간 부담 [C6].
- 임상 리뷰: 부실하거나 과도한 체크리스트는 임상의에게 부담이 되고 효율을 떨어뜨릴 수 있으며, 일부는 "체크리스트가 지능을 모욕한다"고 느낀다. 체크리스트 과부하의 한계는 알려져 있지 않다고 인정한다 [C4]. 설계 논문도 "체크리스트 피로는 충분히 연구되지 않았다"고 인정한다 [C5].
- 의무화: 온타리오의 수술 안전 체크리스트 의무화 연구에서 결과 지표가 개선되지 않았다. 논평은 현지 적응·교육·팀 전체 참여가 핵심이라고 했고, Gawande는 이 연구의 방법론적 문제를 제기했다(AHRQ PSNet 요약. NEJM 원문은 열람 실패, 수치 인용은 하지 않음) [C7].
- Boeing 논문의 결론도 비슷하다: 체크리스트는 전반적 안전 문화·교육과 함께일 때 효과적이고, 미리 짜 둔 절차가 사용자의 경험과 실시간 판단을 대체할 수 없다 [C3].

**번역(추론):** 체크리스트는 숙련자의 누락 방지 장치이지 초심자 교육 장치가 아니다. 초심자 교육은 3.2·3.7·3.6의 안내·예시·용어 설명으로 풀고, 체크리스트는 사용자 소유의 선택 점검 목록(기획 도구 안)으로 한정한다. 효과 근거는 고위험·반복 절차에 있고 지식 탐색 UI에 대한 직접 근거는 없다. 9장 F5.

### 3.5 플레이북·런북형 가이드

- **US Digital Services Playbook [D8]:** 13개 play, 각 play가 도입 서사 + Checklist + Key Questions. "should" 어조의 지침이며 GitHub로 개선 제안을 받는다.
- **Atlassian Team Playbook [D7]:** "어떤 play를 먼저 해야 한다는 정답은 없다"고 밝히고, 진입점을 추천 퀴즈·카테고리·컬렉션으로 나눈다.
- **GOV.UK Service Manual [G15]:** 단계 안내 페이지가 목표 설정·소요·"끝났는지 아는 방법"을 소제목으로 갖는다. Agile delivery 주제 페이지는 발견/알파/베타/라이브/종료 5단계를 나열하되 순차 여부를 명시하지 않으며, 입문 3편을 따로 둔다.
- **NSW Event Starter Guide [E2]:** 스스로를 "매뉴얼이 아니라 출발점"이라 밝히고 15개 주제 모듈과 외부 자료 부록을 둔다.
- **번역(추론):** 세 뷰를 같은 틀(왜 보나 / 무엇을 보나 / 살펴볼 질문)로 표준화하면 플레이북의 '일관된 play 형식' 이점을 얻는다. 런북처럼 순서를 강제하지 않고 상황별 진입점을 제공하는 쪽이 pickDday에 맞다(한국관광 데이터랩의 '우리 지역 행사/축제 성과가 궁금할 때는?' 방식 [E3]).

### 3.6 용어 툴팁(글로서리)

- KRDS 툴팁은 "150자 내외"의 짧은 설명이며 키보드 포커스로도 표시되고 Esc로 닫히며 title 속성과 중복하지 않는다. 상호작용이 필요하거나 더 길면 맥락적 도움말을 쓴다 [K9][K7].
- NN/g: "툴팁을 찾아야만 과업을 끝낼 수 있어서는 안 된다." 마이크로콘텐츠이고, 마우스 호버 전용 구현은 키보드 사용자를 배제하며, 일관되지 않으면 발견되지 않는다 [N9].
- WCAG 1.4.13: 호버·포커스로 나타나는 콘텐츠는 포인터·포커스를 옮기지 않고 닫을 수 있어야 하고(dismissible), 포인터를 그 위로 옮겨도 사라지지 않아야 하며(hoverable), 해제·닫기 전까지 유지돼야 한다(persistent) [A1].
- 번역: 설명 대상은 '지표 정의' 용어(대상·기간·단위 개념). 이는 사용자에게 필요한 정보이며 내부 규칙이 아니다(C3). 9장 F7.

### 3.7 워크드 예시(worked example)

- NSW CESE 보고서(수차례 RCT 요약): 초심자는 문제를 직접 푸는 것보다 풀이 과정이 모두 제시된 예시를 공부할 때 더 잘 배운다(worked example effect). 같은 정보를 글과 그림이 중복하면 학습을 해치고(redundancy effect), 그림과 설명이 떨어져 있으면 두 정보를 머릿속에서 합쳐야 해 부담이 커지므로(split attention) 통합해서 제시해야 한다 [L1]. "중복은 결코 무해하지 않다. 불필요한 정보를 주는 것은 교육 실패의 주된 이유일 수 있다"(Sweller 2016 인용) [L1].
- **expertise reversal:** 전문성이 오르면 예시를 많이 쓰는 것이 점점 효과가 없어지고 중복 또는 역효과가 된다. 안내를 점진적으로 줄이고 독립 문제 해결을 늘리라고 권한다 [L1][L2].
- 빈 화면에서 시연 데이터로 탐색해 보게 하는 접근(NN/g가 든 사례)[N7], 시작용 콘텐츠로 바로 탐색하게 하는 접근[D2]도 같은 계열이다.
- 한계: 근거는 교실·학습 과제이고 전문직 UI에 대한 직접 검증이 아니다.
- 번역: '예시로 읽기' 접이식(첫 방문 이후 기본 접힘), 샘플 표기, 주석을 그래프 위에 통합. 예시가 '모범 답안'으로 읽히지 않게 한다. 9장 F8.

### 3.8 Learn by doing(하면서 배우기) 온보딩

- **active user의 역설:** Carroll·Rosson이 관찰한 바, 사용자는 매뉴얼을 읽지 않고 바로 쓰기 시작한다. "이상적으로 합리적인 사용자가 아니라 실제 행동에 맞춰 설계하라" [N18].
- **minimalist instruction(Carroll):** "의미 있는 과업을 즉시 시작하게 하라", "앞단의 오리엔테이션 자료를 거의 없애라", "오류를 인식하고 복구하는 데 초점을 둬라". 그러나 저자 스스로 이를 체계화한 연역 이론은 없고 반복 시험이 필요하다고 밝힌다 [L6](등급 D, 위키 요약. 원저 미열람).
- **Material(모바일 앱) 온보딩:** 처음 쓰는 사용자에게만 보이고 재방문자에게는 보이지 않으며, 교육을 앞에 강제하지 않고 첫 사용 흐름의 후반(90% 지점)에 제안하는 quickstart 방식 [D3].
- **KRDS:** 코치마크는 사용자 요청 시에만, 4개 이하, '그만보기' 제공 [K8].
- **번역(추론):** 선택기 → 바로 데이터 → 필요할 때 '?'. 라이브 시작 화면에는 이미 '무엇을 볼 수 있는지' 한 문장이 있으므로, 부족한 것은 안내의 양이 아니라 '왜 보는지(목표) · 어떻게 읽는지 · 무엇을 얻는지'일 가능성이 크다(사용자 피드백 원문은 확인하지 못했다). 이 경우 Carroll식 '앞단 자료 최소화'와 F1의 '한 문장 목표'는 충돌하지 않는다.

### 3.9 함정 모음

- **배너 블라인드니스 [N4]:** 사람들은 광고로 인식되는 요소(맞든 틀리든)를 무시한다. 상단 배너·우측 레일 위치, 화려한 서식·색 배경·애니메이션, 작은 직사각형 모양이 광고 신호이고, 광고 곁의 정당한 콘텐츠도 근접성 때문에 광고로 오인된다. 광고로 판정한 영역을 다른 페이지에서도 피한다("hot potato"). 시사(추론): 안내 영역은 본문과 같은 타이포·톤으로 두고, 우측 도움 패널(KRDS 위치)은 '?' 버튼의 발견 가능성은 높이되 패널 자체를 광고처럼 꾸미지 않는다.
- **과잉 안내:** 읽는 양의 한계 [N8], 팁 연속 노출 시 더 빠른 무시 [N3], 튜토리얼 후 더 어렵다는 인식 [N19], 중복 정보의 해악 [L1].
- **체크리스트 피로:** 3.4.
- **expertise reversal:** 초심자에게 필수인 안내가 숙련자에게는 역효과. NN/g는 숙련자용 가속 장치가 초심자에게는 보이지 않게 하는 설계를 권한다 [N11]. 번역(추론): 안내를 첫 방문 노출·기억·재호출 가능 구조로 만든다.
- **자동화 편향·기본값 효과:** 의사결정 지원이 불완전할 때 사용자는 누락·작위 오류를 범하고, 이는 초심자·전문가 모두에게서 나타나며 훈련·지시로 막을 수 없고 개인뿐 아니라 팀에서도 일어난다 [C9]. 기본값 메타분석(58개 연구, 73,675명)은 효과 크기 d=0.68이며, 기본값이 "선택 설계자가 사용자에게 바라는 것"으로 읽힐 때(endorsement) 더 강했다 [C10]. 번역(추론): 기본 탭·기본 정렬·강조 색·'추천' 어휘가 결론처럼 읽히면 C1을 안내 문구가 아니라 설계가 깨뜨린다.

## 4. 비선형 탐색과 권장 순서의 결합

### 4.1 먼저 구분할 것: 폼인가, 애플리케이션인가

NN/g는 선형성을 가장 중요한 기준으로 든다. 사용자가 선형 순서로 진행하고 이전 단계를 다시 보거나 고칠 일이 없으면 폼, 단계를 건너뛰거나 예측할 수 없는 순서로 끝내면 애플리케이션이다 [N17]. 정부 시스템도 같은 선을 긋는다.

- GOV.UK step by step: 읽기만 하거나 순서가 없으면 쓰지 말 것 [G1]
- USWDS: 비선형이면 단계 표시기 부적합 [U1]
- KRDS: 이해에 순서가 중요한 콘텐츠는 탭 대신 단계 마법사 [K3]
- NN/g 마법사: 초심자·드문 과업에는 맞지만, 비교·정보 이전이 필요하거나 전문성이 높으면 부적합하고 사용자 통제를 제한한다 [N2]

pickDday의 두 여정은 세 뷰를 오가며 비교하는 작업이므로 마법사가 아니라 애플리케이션이다. 팀 문서가 이미 "번호가 있는 작성 단계 대신 자유 이동"으로 정한 것과 일치한다.

### 4.2 패턴 후보

| 목적 | 패턴 | 근거 | 주의 |
|---|---|---|---|
| 전체 구조를 한눈에 | 허브(개요)와 스포크(뷰) | NN/g: 스포크 페이지에서 허브로 연결하고 허브끼리 상호 링크하면 사용자가 "그 정보는 없다"고 오해하지 않는다(고객센터 정보 사례) [N13]. KRDS '콘텐츠 내 탐색'은 긴 페이지에서 구성과 현재 위치를 보여준다 [K10] | 허브가 별도 관문 페이지가 되지 않게 |
| 권장 순서 표시 | 약함(기본 탭=첫 탭, "처음이라면" 문구) → 중간(개요 스트립 번호 + '권장' 범례) → 강함(번호 단계·잠금) | Material: non-linear stepper는 "흐름의 어느 지점에서도 진입"을 허용하고 선택 단계는 '선택'으로 표시 [D1]. KRDS 적응형 탐색, 선택 단계는 마지막에 두고 건너뛰기 제공 [K2]. USWDS는 비선형에 step indicator 금지 [U1] | 약함~중간만 사용 |
| 다음 화면 안내 | 패널 끝 이전/다음 링크에 대상 이름 라벨 | GOV.UK Pagination(content sequence)은 이웃 페이지 이름을 라벨로 쓴다 [G9]. step by step은 "지금 할 일과 다음 할 일"을 보여준다 [G12] | 비차단 링크 1개. 이유는 '읽는 목적'만 |
| 방문 상태 | visited(자동) | NN/g: 방문 링크를 다른 색으로 구분하는 것은 "어디에 가 봤는지·어디에 있는지·어디로 갈 수 있는지"를 알려 주는 오래된 표준이며 순환 탐색을 줄인다 [N12]. Atlassian 진행 추적기: visited는 대비를 높이고 클릭해 돌아갈 수 있으며, disabled는 돌아갈 수 없는 단계에만 [D4] | 색만으로 전달 금지 [A6][K14]. 기록은 탐색 기억이지 성취가 아니다 |

| 시작점 찾기 | 상황별 진입 문장 또는 몇 개의 질문 | CHR&R: "어디서 시작할지 모르겠다면 Getting Started에서 몇 가지 질문에 답해 가장 알맞은 시작점과 도구를 찾으라" [E1]. Atlassian Team Playbook의 추천 퀴즈 [D7]. 한국관광 데이터랩의 "우리 지역 행사/축제 성과가 궁금할 때는?" [E3] | pickDday는 홈에서 이미 두 여정으로 분기한다. 추가 분기는 과설계 위험(추론) |
| 탭 간 비교 | 담기·비교 요약 | 탭은 비교에 부적합 [G5][K3][N6]. pickDday에는 '담은 근거'가 있다 | 비교 기능이 기록을 강제하지 않게(C2). 이 항은 추론 |

### 4.3 비선형 UI에서 하지 말 것

- 번호+잠금, disabled 탭 [K3][D4]
- "N/3 완료" 같은 진행 막대와 완료율 지표(팀 원칙: 가치는 기록 개수나 완료율이 아님)
- '다음'을 눌러야만 이동하는 구조, 첫 방문에만 뜨는 모달 투어 [K8][N5]
- 방문 상태를 색으로만 구분 [A6]
- 저장 위치(이 기기 한정)를 알리지 않고 상태를 보여 주는 것

### 4.4 구성 제안(텍스트 도식, 추론)

```

      · 한 문장 목표
      · 볼 수 있는 화면 3개: 아이콘 + 이름 + 한 줄, '처음이라면' 범례가 달린 권장 순서 스트립

        [패널 끝] 이어서 살펴볼 화면 링크 1개 · 참고 자료 2~3개(접이식) · '살펴봤어요' 토글(선택)
```

|---|---|---|
| 정보 전달(차트·지도·도식) | KRDS: "사용자에게 정보를 전달하는 데 텍스트보다 이미지가 적합한 경우"에 사용 [K15]. GOV.UK: 다이어그램은 "내용을 더 명확히 하거나 많은 양을 요약할 때"만 [G14]. NN/g: 관련 정보를 담은 이미지는 주의 깊게 본다 [N14] | 이미지 속 텍스트 금지, 텍스트 동등물 제공 [G14][A10] |
| 길찾기·정체성(홈의 큰 일러스트) | 팀이 확인한 사용자 호평. Atlassian: 일러스트는 "사용자의 맥락과 감정 상태를 반영"해야 [D5] | 홈과 여정 시작에 한정(추론) |
| 빈 화면·첫 사용 | NN/g: 시스템 상태를 알리고, 학습 단서를 주고, 시작할 수 있는 직접 경로(링크)를 준다 [N7]. Atlassian: spot 일러스트를 빈 상태·오류 상태·성과 축하에 사용 [D5]. Material: 이미지는 배경에 은은하게, 문구는 CTA처럼 쓰지 않는다(눌러야 하는 것으로 오인) [D2] | 행동 연결 필수 |
| 기능 소개·온보딩 | Atlassian: 실제 스크린샷 대신 기본 도형·회색조의 저충실도 UI 도식을 써서 혼동을 피한다 [D5] | 실제 캡처는 낡기 쉽다(추론) |
| 아이콘 + 레이블 | NN/g: 아이콘 의미는 경험에 의존해 모호하므로 텍스트 레이블을 항상 함께 보여야 하고 호버 전용은 안 된다 [N16]. (검색 결과 요약에는 "레이블 있는 내비게이션이 20% 빠르고 확신이 높았다(76명, 2014)"는 NN/g 시험이 있으나 해당 기사에서 직접 확인하지 못해 수치는 미확인) | 레이블 상시 노출 |
| 프로세스 개요 | USWDS process list는 항목 안에 이미지·버튼·표를 담을 수 있다 [U2] | 도식은 설명과 통합(split attention 방지) [L1] |

### 5.2 이미지가 해가 되는 경우

- **장식:** NN/g 시선 추적에서 순수하게 장식적인 "분위기용(feel-good) 큰 이미지"는 완전히 무시된다 [N14]. 지그재그 이미지-텍스트 배치에서는 장식 이미지를 무시하기 어려워 사용자가 "장애물 코스"처럼 피해 읽는다 [N15]. 학습 연구: 흥미롭지만 무관한 세부 정보(seductive details)는 기억에 작은 해악, 전이에 중간 해악(Rey 2012 메타분석을 인용한 보고) [L3][L4], 장식 이미지는 e-learning에서 이해에 소폭 해로웠고 주의 억제 능력이 낮은 사용자에게 더 컸다 [L4]. 다만 좋은 멀티미디어 설계의 효과는 복잡한 자료와 시스템이 속도를 정하는 환경(강의)에서 더 크고 자기 속도(웹사이트)에서는 작다 [L5]. (추론) 데이터 읽기 화면에서 장식은 이득 없이 비용만 있고, 읽기 과제가 아닌 홈·시작에서는 비용이 작을 수 있다.
- **중복·분리:** 글과 그림이 같은 내용을 반복하면 redundancy, 그림과 설명이 떨어져 있으면 split attention [L1].
- **성능:** KRDS는 이미지가 화면 로딩 속도를 늘린다고 경고한다 [K15]. LCP는 75% 방문에서 2.5초 이하를 목표로 한다 [A12].
- **의미를 이미지로만 전달:** GOV.UK "이미지만으로 정보를 제공하지 말라" [G14]. WCAG 1.1.1 [A5].
- **CTA처럼 보이는 일러스트·문구** [D2].

### 5.3 일관된 일러스트 체계(스타일 가이드에 둘 항목)

| 항목 | 규칙 | 근거 |
|---|---|---|
| 유형 정의 | Hero(홈·여정 시작) / Spot(빈·첫 사용·오류 상태, 단계 안내) / Icon(항상 레이블 병기) / 정보 시각화(차트·지도) | Atlassian이 spot, 저충실도 UI, ambient pattern으로 구분 [D5]. KRDS가 이미지와 아이콘을 구분 [K15][K16] |
| 크기 | 아이콘은 KRDS 기준 24px(16/20/24/32/40, 4·8px 배수). Hero·Spot은 자체 정의 | [K16]. Hero·Spot 크기 수치는 출처 없음(제안) |
| 색 | 디자인 토큰으로 관리, 의미를 전달하는 그래픽은 인접색과 3:1 | KRDS 토큰 체계 [K19], WCAG 1.4.11 [A2] |
| 형태 | 선/면 구분, 정면 시점, 단순한 형태로 일관 | KRDS 아이콘 [K16] |
| 인물·표현 | 같은 인물 표현 체계를 유지하고 대표성을 점검 | Atlassian이 추상 캐릭터에서 다양한 표현으로 개편한 경위 [D6] |
| 재사용 | 같은 의미에 같은 그림, 단일 자산 저장소(추론) | - |
| 접근성 메타 | 자산마다 '장식/정보/기능' 분류와 alt 정책을 기록 | W3C WAI [A10] |

### 5.4 접근성

- **장식 이미지:** `alt=""`(alt 속성 자체를 생략하면 일부 스크린 리더가 파일명을 읽는다). 가능하면 CSS 배경으로 제공 [A10]. KWCAG 2.2 5.1.1도 장식에는 공백 대체 텍스트를 요구한다(커뮤니티 HTML 사본 확인, 공식 문서는 미열람) [A11].
- **정보 이미지:** 문자 그대로의 묘사가 아니라 의미·목적을 전하는 짧은 대체 텍스트 [A10].
- **복잡한 이미지(차트·프로세스 도식):** 짧은 설명 + 긴 설명(같은 쪽의 본문, figure/figcaption, 표) [A10]. GOV.UK는 차트 아래 설명, 원자료 표, 접근 가능한 파일 링크 중 하나 이상을 둔다(자사 게시 도구 지침) [G14].
- **대비·색:** 이해에 필요한 그래픽은 인접색과 3:1이며 가는 선은 안티앨리어싱으로 흐려질 수 있다 [A2]. 색만으로 정보를 전달하지 않는다(방문 상태 표시 포함) [A6][K14].
- **확대·리플로우:** 200% 확대에서 내용·기능 손실이 없어야 하고 [A3], WCAG 2.1 AA에는 320 CSS px 폭(1280px 창의 400% 확대에 해당)에서 2차원 스크롤 없이 읽는 Reflow도 포함된다(지도·도식·표는 예외 가능) [A4]. 사용자의 '200% 확대' 요건보다 엄격하므로 400%까지 시험하는 편이 안전하다. 일러스트는 고정 높이·절대 배치를 피하고 좁은 폭에서 세로로 쌓이거나 생략되게 한다(KRDS도 폭이 부족하면 이미지 제거·크롭을 고려하라고 함 [K15]).
- **아이콘:** 레이블 없는 아이콘 금지 [N16].
- **도움 패널·툴팁:** 호버 콘텐츠는 1.4.13 충족 [A1]. WCAG 2.2(참고)에서는 고정 헤더·패널이 키보드 포커스를 완전히 가리면 안 되고(2.4.11 AA) [A7], 도움 수단은 페이지마다 같은 상대 위치에 둔다(3.2.6 A) [A8].

### 5.5 성능

- LCP를 75% 방문에서 2.5초 이하로, LCP 이미지는 **lazy-load 금지**하고 `fetchpriority="high"`를 고려 [A12].
- 폴드 아래 이미지는 `loading="lazy"`, `width`·`height`를 명시해 레이아웃 이동을 막는다 [A13].
- 해상도·크기별 이미지는 `srcset`·`sizes`로 브라우저가 고르게 하고, 아트 디렉션이 필요하면 `<picture>` [A14].
- 차트·다이어그램·아이콘은 SVG 우선 [G14][K16].
- 번역(추론): 홈의 큰 일러스트는 LCP 후보일 가능성이 높으므로 즉시 로드하고 우선순위를 주며, 하위 화면의 보조 일러스트는 lazy-load.

### 5.6 "모든 페이지에 이미지" 요구를 번역하는 예산표(제안)

| 페이지 유형 | 권장 시각 요소 | 피할 것 |
|---|---|---|
| 홈 | 큰 일러스트 2장(호평, 유지) + 한 줄 설명 | 같은 크기·구도를 하위 화면에 반복 |
| 여정 시작(선택기) | 작은 spot 1개 + 3개 뷰 도식(아이콘+라벨) | 선택기를 폴드 아래로 미는 히어로 |
| 여정 데이터 화면(탭) | 차트·지도가 주인공, 아이콘+라벨 | 장식 일러스트, 차트 곁에 같은 내용을 반복하는 그림 |
| 빈·오류·첫 사용 상태 | spot(작게) + 짧은 문구 + 다음 행동 | 행동 없는 그림, CTA처럼 보이는 문구 |
| 기획 도구 | 아이콘+라벨, 텍스트 상태 라벨 | 큰 일러스트(작업 화면 밀도 저하) |
| 도움 패널 | 필요할 때 작은 도식 1개 | 패널 안 장식 |

## 6. 초심자를 다단계 계획·행정 절차로 안내한 참고 사례

각 사례는 열람한 범위만 평가했다. 사례의 UX 품질을 독립 측정한 근거는 없고, 성과 수치는 운영 기관의 보고다.

### R1. GOV.UK "Learn to drive a car: step by step" — 행정 절차 안내의 표준형 [G1][G12][G13]

- **무엇:** 면허 취득 과정을 한 장의 여정 지도로 보여 준다(콘텐츠 API 기준 7개 항목: 허용 여부 확인 → 임시 면허 → 연습 → 이론 시험 준비(병렬 "and") → 이론 시험 → 실기 시험 → 합격 후). 단계 아래에 해야 할 일 링크와 비용(£34~£43, £23, £62~£75)이 붙는다. 컴포넌트에는 열어 둔 단계를 `sessionStorage`에 기억하는 기능이 있다(해당 페이지가 이 기능을 켰는지는 확인하지 못했다).
- **배울 점:** (1) 시작과 끝이 한눈에 보이는 지도. GDS는 과업 완료 성공과 이용 자신감이 의미 있게 늘었다고 보고한다(독립 검증 아님). (2) 링크 옆에 비용 같은 판단 정보를 붙이는 방식. (3) and/or로 병렬·대안을 표현. (4) 열어 둔 상태 기억.
- **피할 점:** 번호와 순서 강제. 이 패턴은 순서가 있는 여정용이다. GOV.UK 스스로도 "사용자가 머리글을 거의 쓰지 않는다", "여러 step by step 사이를 오가며 좌절한다"를 알려진 문제로 적는다 [G1]. 지도를 여러 겹으로 두지 않는다.
- **pickDday 매핑:** 개요 스트립의 정보 구성(이름 + 한 줄 + 읽는 데 쓰는 자료·기준)만 차용.

### R2. County Health Rankings & Roadmaps "Take Action Cycle" (Community Tool Box 해설) — 지역 담당자용 비선형 사이클 [E1]

- **무엇:** 6단계 사이클(Work Together / Assess Needs & Resources / Focus on What's Important / Choose Effective Policies & Programs / Act on What's Important / Evaluate Actions). "지역 건강 개선 노력은 사이클의 어느 지점에서도 시작할 수 있다"고 밝히고, 어디서 시작할지 모르면 "Getting Started에서 몇 가지 질문에 답해 가장 알맞은 시작점과 도구를 찾으라"고 안내한다. 각 단계에 맞춤 안내와 도구가 있고, 해설 섹션은 What / Why / When / Who / How 5개 질문으로 열리며 체크리스트·예시·도구·슬라이드는 별도 페이지다.
- **열람 범위:** Community Tool Box 페이지는 직접 열람(문장 대조). CHR&R 사이트 자체는 403이라 실제 화면 UX는 확인하지 못했다.
- **배울 점:** 순서 없는 사이클 + 시작점 찾기 질문 + 일관된 섹션 틀 + 체크리스트를 본문과 분리.
- **피할 점:** 범용 툴킷의 방대한 텍스트(읽는 양의 한계 [N8]). 시작점 질문이 입력 관문이 되는 것.

### R3. NSW Event Starter Guide — 행사 기획 초심자용 정부 가이드 [E2]

- **무엇:** NSW 주정부(Premier's Department) 공공·야외 행사 조직자용 가이드. 스스로를 "출발점이지 매뉴얼이 아니다"라고 규정하고, 15개 주제 모듈(문서, 위험 평가, 안전, 소통, 보건, 교통, 접근성, 지속가능성, 자원봉사자, 공연자, 모금, 후원, 의전, 사전 활동, 평가)과 질문 11개의 'Before you begin', 외부 자료 부록으로 구성된다.
- **열람 범위:** 랜딩, before-you-begin, documentation 페이지(요약 열람).
- **배울 점:** 작업보다 질문을 먼저 던지는 구성. "행사를 추진하기 전에 핵심 질문에 답하면 시간과 비용을 크게 아낄 수 있다"는 프레이밍. 병렬 주제 모듈. 겸손한 포지셔닝.
- **피할 점:** 열람 요약 기준으로 랜딩에는 체크리스트·타임라인·템플릿이 없고 실행 도구를 찾으려면 각 모듈로 들어가야 한다. documentation 페이지는 산문·불릿 위주에 "should / need to" 어조가 단정적이고 템플릿이 없다. pickDday는 C1에 맞춰 중립 어조를 유지한다.

### R4. 한국관광 데이터랩(한국관광공사) — 국내 지자체 담당자가 아는 관광 데이터 서비스 [E3]

- **무엇:** 이동통신·카드·내비게이션 등 관광 빅데이터 분석 서비스. 홈에 '서비스 활용 가이드'가 있고 상황 문장이 진입점이다("우리 지역 행사/축제 성과가 궁금할 때는?", "한국방문 외국인들의 항공기 이용 현황이 궁금할 때는?", "우리 지역의 관광 마케팅 포인트가 궁금할 때는?"). '많이 찾는 메뉴' 7개와 지역별·국가별·마이 데이터랩 대시보드가 있다.
- **열람 범위:** 홈과 소개 페이지(요약 열람). 소개 페이지는 지역·국가·산업·테마 카테고리 중심 메뉴와 FAQ·고객문의로 구성되고 용어 설명이나 튜토리얼은 눈에 띄지 않는다는 요약을 얻었다. 한국관광공사 관광e배움터의 데이터랩 교육 과정(30분·50분)은 검색 결과 요약에서만 확인했다(미확인). 데이터랩 내부 분석 화면은 열람하지 않았다.
- **배울 점:** 과업 언어(상황 문장)로 진입시키는 방식. pickDday의 '두 여정' 분기와 같은 철학이다. 공무원이 이미 아는 서비스이므로 차별화 지점의 기준이 된다.
- **격차(추론):** 기능·카테고리 중심 메뉴라 초심자의 '이 데이터를 어떻게 읽고 무엇을 판단하는 데 쓰는가' 안내는 약해 보인다. pickDday는 이 부분을 화면 안에서 짧게 채울 수 있다.

### R5. 플레이북 형식 — GOV.UK Service Manual, US Digital Services Playbook, Atlassian Team Playbook [G15][D8][D7]

- **무엇:** 초심자가 많은 실무자 집단에게 "무엇을 하는지, 왜, 끝났다는 것을 어떻게 아는지"를 같은 틀로 제시한다. GOV.UK는 단계 페이지에 목표·소요·종료 기준 소제목, USDS는 play마다 서사 + Checklist + Key Questions, Atlassian은 "어떤 play를 먼저 해야 한다는 정답은 없다"며 추천 퀴즈를 제공한다.
- **배울 점:** 일관된 틀, 선택성을 문장으로 명시("멈추는 것은 실패가 아니다"), 상황별 진입.
- **피할 점:** Checklist가 의무로 읽히는 어조. USDS는 스스로 "should 어조의 지침이며 의무가 아님"을 밝힌다. 이 형식의 효과를 측정한 연구는 찾지 못했다.

### 보조 사례

- **KRDS 서비스 패턴 '신청' [K17]:** 대상 탐색 → 신청서 작성(작성 매뉴얼 확인·서류 제출·임시 저장) → 확인/확정 → 결과 확인. 첫 단계는 '유의 사항·자격 확인'이며 신청과 무관한 정보는 넣지 않는다. 신청 과정·처리 절차 정보 제공이 필수 수준이다. 배울 점은 안내를 절차 앞에 두고 무관한 정보를 빼는 것, 임시 저장 개념(pickDday에서는 '이 기기에 저장됨' 상태 표시와 대응, 추론). 제출 중심 모델이라 탐색에는 그대로 맞지 않는다.
- **정부24 메인 [E4](정적 열람만):** 생애주기별 '원스톱 서비스'(전입신고, 맘편한 임신, 행복출산), 자주 찾는 서비스, 보조금24의 '맞춤안내 조회'가 보였고, 처음 이용자를 위한 구조화된 안내는 눈에 띄지 않는다는 요약을 얻었다. 내부 단계 안내는 열람하지 않아 품질은 평가하지 못했다.

## 7. 검증이 필요한 가설과 시험 제안

소규모 형성평가(지자체 담당자, 처음 맡은 사람과 경험자 섞어서)를 권한다. 'Checklist for Checklists'도 현장 사용자와 실제·모의 상황에서 시험하고 반복 수정하라고 말한다 [C1].

| # | 질문 | 방법 | 신호 |
|---|---|---|---|
| H1 | 시작 화면의 목표 + 3화면 소개를 5초 보고 "이 여정으로 무엇을 하는지" 설명할 수 있는가 | 5초 시험 + 말로 설명 | 설명의 정확도, 오해("결정해 준다") 비율 |
| H2 | '처음이라면' 권장 순서가 자유 이동을 막는가, 길잡이로 쓰이는가 | 과업 관찰, 이동 순서 기록 | 순서 준수율이 아니라 이동 후 되돌아오는 빈도·인식 인터뷰 |
| H3 | '살펴봤어요' 표시가 완료 압박을 만드는가 | 사용 전후 인터뷰, 사용률 | "다 눌러야 할 것 같다"는 진술 |
| H4 | 도움 패널의 최초 1회 열림이 발견을 돕는가, 광고처럼 무시되는가 | 시선 추적 또는 발화 사고, 열기·닫기·재호출 기록 | 패널 내용을 읽었는가, 재호출 |
| H5 | 읽을거리 2~3개가 쓸모 있다고 느껴지는가 | 클릭·인터뷰 | 기대 대비 실제 도움 |
| H6 | 장식 일러스트를 뺀 데이터 화면과 넣은 화면의 스캔·이해 차이 | 소규모 비교 | 과업 시간, 이해 질문 정답률 |
| H7 | 키보드만, 200%·400% 확대, 스크린 리더로 탭·도움 패널·툴팁을 쓸 수 있는가 | 실사용 보조기술 시험 | 막힘 지점 |
| H8 | 처음 맡은 담당자가 인수인계 없이 시작하는 상황에서 어떤 안내가 필요한가 | 인터뷰·관찰 | 질문 목록 |

- **순환보직 맥락(참고):** 중앙부처 과장급 이상 공무원의 평균 재직기간이 "1년 남짓"이라 인수·인계의 비효율과 전문성 축적 저하를 낳는다는 KDI 연구가 있다 [X1](중앙부처 대상, 연도 미확인). 지자체 축제 담당자에게 그대로 적용할 수는 없고 가정으로만 쓴다. 상태가 브라우저에만 남는 제약(C5) 아래서 인수인계를 돕는 선택 기능(예: 사용자가 직접 내보내는 요약 파일, 기획안·출력 활용)은 가설로 검토할 수 있으나 이번 조사 범위 밖이다(추론).
- **KRDS 준수:** 도입 기관은 필수·권장·우수 수준 점검을 하므로 [K17][K19], 공공 발주·도입 맥락이라면 어떤 KRDS 컴포넌트를 쓰고 어떤 것은 의도적으로 쓰지 않는지(예: 단계 표시기) 사유를 정리해 두면 설명 비용이 줄 수 있다(추론).

**이번 조사에서 확인하지 못한 것**

- 읽을거리 목록·목표 헤더·권장 순서 표시가 성과를 높인다는 직접 증거.

- GOV.UK step by step의 실제 상호작용(Show all 등)과 KRDS·GOV.UK 컴포넌트 실제 렌더링.

### F1. 시작 화면에 목표·보게 될 것·읽는 법을 선택기 옆에 한 덩어리로

- **패턴:** GOV.UK Start using a service [G8], KRDS 신청 패턴의 '유의 사항·자격 확인'(첫 단계, 무관한 정보 제외) [K17], Service Manual 단계 안내(목표·소요·종료 기준) [G15], KRDS 안내 영역(본문 상단, 화면당 하나) [K4].
- **근거:** GOV.UK는 시작점이 "서비스가 무엇을 하는지, 내 필요에 맞는지" 알 만큼만 설명하고 복잡한 자격 조건은 서비스 안에서 묻게 한다 [G8]. 평균 웹 페이지에서 읽히는 단어는 20% 안팎이다 [N8]. 라이브 시작 화면에는 이미 '무엇을 볼 수 있는지' 한 문장이 있다 [X2].
- **제안:** 이미 필요한 선택 입력(축제 / 시군구) 곁에 3층 블록을 둔다.
  1. 한 문장 목표 — 예(기존 축제): "다음 회차를 준비하는 데 참고할 방문 흐름·주변 관광자원·개최 시기 자료를 한곳에서 살펴봅니다."
  2. 볼 수 있는 화면 3개 — 아이콘 + 이름 + 한 줄(F2의 개요 스트립과 같은 요소).
  3. "입력 없이 볼 수 있어요" 한 줄.
  별도 페이지·모달로 만들지 않아 클릭 수가 늘지 않는다. 현재 문구에 '왜 보는지·어떻게 읽는지·무엇을 얻는지'를 보강하는 수준이다.
- **피할 위험:** 시작 전 확인이 관문처럼 작동하는 것(C2). 방문마다 같은 안내가 반복돼 무시되는 것 [N5]. 목표를 "결정"으로 쓰는 것(예: "최적 시기 결정") — 데이터가 정답을 낸다는 인상을 준다(C1).
- **제약:** C1, C2, C3.

### F2. 권장 순서는 탭 바깥(개요 스트립·다음 링크)에서만 알린다

- **패턴:** KRDS 탭 [K3], USWDS 단계 표시기의 비선형 경고 [U1], KRDS 단계 표시기의 적응형 탐색 [K2], Material non-linear stepper [D1], GOV.UK Pagination(content sequence) [G9], GOV.UK step by step의 '쓰지 말 경우' [G1].
- **근거:** 순서가 중요한 콘텐츠에는 탭이 부적합하다고 KRDS와 GOV.UK가 모두 말한다 [K3][G5]. 반대로 "첫 섹션이 대부분에게 가장 중요한 경우" 탭이 적합하다고도 한다 [K3][G5] — 현재 설계(기존 축제는 과거 방문 흐름이 첫 탭)와 부합한다. 비선형 흐름에 단계 표시기를 쓰면 폼으로 오인된다 [U1].
- **제안:** 탭 레이블에는 번호·잠금을 쓰지 않는다. 권장 순서는 (a) 시작 화면·도움 영역의 3칸 스트립에 "처음이라면 이 순서로 보면 흐름이 이어져요 · 순서는 자유예요" 범례와 함께 두고(좁은 폭에서는 세로 목록), (b) 각 패널 끝에 "이어서: 주변 관광자원 — 이 지역의 관광지·문화시설을 살펴봅니다" 같은 링크 1개(라벨에 대상 이름, 이유는 '읽는 목적'만)로 알린다. 팀이 번호 단계를 쓰지 않기로 했으므로 번호 없이 '처음이라면 → 이어서 → 마지막으로' 어휘를 쓰는 변형도 가능하다.
- **피할 위험:** 번호 stepper가 폼처럼 보이는 것. disabled 탭 [K3]. 권장 순서가 '결론 순서'로 읽히는 것(개최 시기가 마지막에 있다는 이유로 "답"이 거기 있다고 읽힘, 추론). 탭 간 비교가 필요한 상황 [K3][G5] — F3·F9의 담기·요약과 연결해 보완(추론).
- **제약:** C2, C4.

### F3. 진행은 '방문함'(자동)과 '살펴봤어요'(선택)로 나누고 완료율을 쓰지 않는다

- **패턴:** 방문 링크 구분 [N12], Atlassian 진행 추적기의 visited 상태 [D4], GOV.UK의 자기 선언 완료 라디오 [G3], KRDS 배지(텍스트 레이블, 4.5:1, 한 요소에 하나) [K14], WCAG 1.4.1 [A6], GOV.UK step by step의 상태 기억 [G11].
- **근거:** 방문 표시는 "어디에 가 봤는지·어디에 있는지·어디로 갈 수 있는지"를 알려 주는 오래된 탐색 표준이고 [N12], GOV.UK는 상태가 많을수록 기억하기 어려우니 최소로 시작하라고 한다 [G3]. 팀 원칙도 제품 가치를 "기록 개수나 기획안 작성 완료율"이 아니라 정보의 확보·비교·이해로 본다.
- **제안:** (1) '방문함'은 자동·중립 텍스트 라벨(색 단독 금지). (2) '살펴봤어요'는 사용자가 누르는 토글(`aria-pressed`)로 선택 제공하고 요약은 개수까지만, 퍼센트·막대·'완료' 어휘 금지. (3) 저장은 localStorage + try/catch(차단 시에도 UI 정상, 세션 메모리로 대체), "이 기기에만 저장돼요" 한 줄과 초기화 제공.
- **피할 위험:** 진행 표시가 목표가 되어 보지 않아도 될 화면까지 채우게 만드는 완료 압박(행동경제 문헌에 알려진 현상이나 이번 조사에서 원 논문은 열람하지 못함 → 가설). 공용 PC에서 남의 표시가 보이는 것. 색만으로 상태 전달. 저장소 차단 시 화면이 깨지는 것.
- **제약:** C2, C4, C5.

### F4. 화면마다 고정형 안내 영역 하나: 읽는 법 + 살펴볼 질문

- **패턴:** KRDS 도움 기본 패턴의 고정형 도움말 [K4], Community Tool Box의 5질문 틀 [E1], USDS Playbook의 서사 + Key Questions [D8], NSW 'Before you begin'의 질문형 [E2].
- **근거:** KRDS는 안내 영역을 본문 상단에, 화면당 하나로, 필수 정보는 인라인 텍스트로 두라고 한다 [K4]. NSW는 초기 고려사항을 질문으로 제시한다 [E2]. 팀 문서도 가이드를 "무엇을 고려하고 자료를 어떻게 읽으며 어디까지 판단할 수 있는지 안내"하는 것으로 정의하고 답변 작성·저장 없이 읽을 수 있어야 한다고 한다 [X2].
- **제안:** 안내 영역을 3줄 이내로 구성한다. ① 이 화면에서 보는 것, ② 읽는 법(지표의 대상·기간·단위 — 예: "이 그래프는 지역 전체 방문 추정이며 행사장 입장객이 아닙니다"는 사용자에게 필요한 정보), ③ 살펴볼 질문 2~3개(문장형·체크 상태 없음, 예: "축제 기간 전후로 방문이 어떻게 달랐나요?"). '결정할 것' 대신 '살펴볼 질문' 어휘를 쓴다.
- **피할 위험:** 질문이 설문·체크리스트로 변질. "이 시기가 유리합니다" 같은 결론 문장. 매 화면 반복되는 장문. 내부 수집·검증 규칙의 노출(C3) — 사용자에게 필요한 데이터 한계('무엇을 기준으로 한 값인가')와 내부 절차를 구분한다.
- **제약:** C1, C2, C3.

### F5. 체크리스트는 탐색에 두지 않고, 기획 도구의 선택 점검 목록으로 한정한다

- **패턴:** Checklist for Checklists [C1], Boeing의 준비형 체크리스트 [C3], DO-CONFIRM [C5][C8], GOV.UK Complete multiple tasks의 변형 [G3].
- **근거:** 체크리스트 설계 문서는 "A checklist is NOT a teaching tool or an algorithm"이라 적고 항목을 누락 위험이 큰 핵심 단계로 한정한다 [C1]. 길이·습관화에 따른 단축 응답 [C2], tick-box 인식 [C6], 의무화의 불확실한 효과 [C7].
- **제안:**
  1. 데이터 탐색 화면에는 체크리스트를 두지 않고 F4의 '질문'만 둔다.
  2. 기획 도구(예산·준비·기획안)에 한해 사용자 소유의 선택 점검 목록을 제공한다. DO-CONFIRM형(자기 방식으로 진행하고 멈춰서 확인), 항목 9개 이하, '해당 없음'·'나중에' 허용, 이동 비차단, 완료율 미표시, localStorage.
  3. 기획 도구 허브는 GOV.UK 작업 목록을 변형한다. 상태는 "있음 / 아직 없음" 수준의 개수 표시로 줄이고 'Cannot start yet'과 "모두 Completed여야 진행" 규칙은 제거한다 [G2][G3].
  4. 확인 필요: 홈의 세 번째 진입("내 축제 작업 시작")이 두 여정과 같은 위계로 보이면 기록이 필수처럼 읽힐 수 있다. 시각 위계로 선택성을 전달한다(라이브 화면의 실제 위계는 요약 열람이라 미확인).
- **피할 위험:** 점검 항목이 '필수 절차'나 법정 의무처럼 읽히는 것. 항목이 늘어 형식화되는 것. 교육 목적을 체크리스트로 해결하려는 시도(교육은 F4·F7·F8).
- **제약:** C2, C3.

### F6. 도움 패널·코치마크는 요청형, 패널은 최초 1회만 열고 기억한다

- **패턴:** KRDS 도움 패널·코치마크·따라하기 패널 [K5][K6][K8], NN/g pull 대 push [N5][N10], 튜토리얼 시험 [N19], 오버레이 [N3], WCAG 2.4.11(2.2 참고) [A7].
- **근거:** KRDS 도움 패널은 로드 시 열린 상태로 제공해 존재를 알리고, 필수 정보는 본문에 두며, 폭이 좁으면 열기 버튼 + 모달로 전환한다 [K5]. 코치마크는 자동 실행 금지·4개 이하 [K8]. NN/g 시험에서 튜토리얼은 과업 성공을 높이지 못하고 난이도 인식을 높였다 [N19](모바일 앱 한계).
- **제안(추론):** 우측 '?' 도움 패널을 KRDS 방식으로 제공하되 최초 방문에만 열고 닫으면 localStorage로 기억해 '?'로 다시 연다(KRDS의 발견 가능성 원칙과 NN/g의 쉬운 닫기·재호출을 함께 충족). 코치마크는 "이 화면 사용법 보기" 버튼으로만 시작하고 4단계 이하. 패널 외형은 본문과 같은 타이포·톤으로 두어 광고처럼 보이지 않게 한다 [N4]. 폭이 좁거나 200% 확대에서는 모달로 전환하고 Esc 닫기·포커스 복귀를 보장한다.
- **피할 위험:** 로드 시 자동 오버레이. 해석에 필수인 정보가 패널에만 있는 것. 우측 레일이 배너처럼 무시되는 것 [N4]. 고정 패널이 키보드 포커스를 가리는 것 [A7].
- **제약:** C3, C4, C5.

### F7. 지표 용어는 짧은 툴팁 + 긴 설명은 맥락적 도움말, 필수 해석은 본문에

- **패턴:** KRDS 툴팁(150자 내외)·맥락적 도움말 [K9][K7], NN/g 툴팁 지침 [N9], WCAG 1.4.13 [A1].
- **제안:** 설명 대상은 '지표 정의' 용어(대상·기간·단위 개념, 예: '일평균', '추정', '관측연도'). 툴팁은 150자 내외, 키보드 포커스로 열고 Esc로 닫으며 포인터를 옮겨도 유지되고, 터치에서는 탭으로 연다. 더 긴 설명은 맥락적 도움말·도움 패널로 보낸다. 대상·기간·단위처럼 해석에 필수인 정보는 항상 본문에 노출한다.
- **피할 위험:** 필수 정보를 툴팁에만 두는 것 [N9][K7]. 호버 전용 구현 [N9]. title 속성 중복 [K9]. 용어 밑줄 남발로 읽기가 끊기는 것.
- **제약:** C3, C4.

### F8. 예시는 '읽는 법 예시'로, 접이식·샘플 표기·정답 제시 금지

- **패턴:** worked example effect와 expertise reversal, redundancy, split attention [L1], 빈 화면의 시연 데이터 [N7], 시작용 콘텐츠 [D2].
- **제안:** 뷰마다 '예시로 읽기' 접이식 1개. 이미 있는 논산 샘플 같은 실제 데이터로 차트 읽는 법을 그래프 위 주석으로 통합한다(분리된 범례 금지). '예시' 라벨을 붙이고 첫 방문 이후 기본 접힘(기억).
- **피할 위험:** 예시가 '모범 답안·최적 시기'로 읽히는 것(기본값·앵커 효과 가능성 [C10], 앵커링은 이번 조사에서 별도 검증하지 않음). 숙련자에게 중복되는 것 [L1]. 샘플과 사용자가 고른 실제 대상이 혼동되는 것.
- **제약:** C1, C3.

### F9. 읽을거리는 단계당 2~3개, 목적·형식·출처를 붙이고 링크로 안내한다

- **패턴:** KRDS 도움 패널 푸터의 관련 링크 [K5], 정책 정보 확인 패턴의 '정책 자료 참고' 단계 [K17], GOV.UK step by step의 링크 + 비용 표기 [G1][G13], NSW의 외부 자료 부록 [E2].
- **근거:** 읽을거리 목록의 효과를 직접 시험한 연구는 찾지 못했다(가설). KRDS는 상세 정보를 "정확하고 최신화된 상태로" 제공하는 것을 필수 수준으로 둔다 [K17].
- **제안:** 도움 패널 푸터 또는 패널 끝 접이식에 2~3개. 각 항목은 '무엇을 알 수 있는지 한 줄 + 발행기관·연도·형식·용량 + 새 탭 안내'. 후보(내용 검토는 하지 않음, 게시 확인만): 행정안전부 「지역축제장 안전관리 매뉴얼(2024)」 — PDF 27.4MB, 2024-10-15 게시 [E5]. 문화체육관광부 「2024 문화관광축제 종합평가보고서」 — PDF 18MB, 2025-04-04 게시, 공공누리 4유형(출처표시·상업적이용금지·변경금지) [E6]. 변경금지 조건 때문에 내용을 가공해 옮기지 말고 링크로 안내한다(라이선스 해석은 확인 필요, 미검증).
- **피할 위험:** '필독'으로 읽히는 것(C2). 링크 부패와 낡은 자료. 대용량 파일을 모르고 여는 것. 라이선스 위반.
- **제약:** C2, C3.

### F10. 시각 요소는 예산·유형 체계로 관리한다

- **패턴:** Atlassian 일러스트 지침 [D5], NN/g 사진·지그재그·빈 상태 [N14][N15][N7], KRDS 이미지 [K15], seductive details [L3][L4][L5], Material 빈 상태 [D2].
- **근거:** 장식은 시선에서 무시되거나 이해를 소폭 해치고, 정보를 싣는 이미지와 행동이 이어지는 상태 일러스트는 근거가 있다(5장). 홈의 큰 일러스트에 대한 사용자 호평은 길찾기·정체성 기능으로 해석하는 것이 안전하다(추론).
- **제안:** 4유형(Hero / Spot / Icon / 정보 시각화)과 5.6의 페이지 유형별 예산표를 스타일 가이드에 둔다. '모든 페이지에 이미지'를 '모든 페이지에 목적 있는 시각 요소(데이터 시각화, 도식, 상태 일러스트, 레이블 있는 아이콘)'로 번역한다.
- **피할 위험:** 홈의 호평을 모든 페이지로 일반화하는 것. 지그재그 배치 [N15]. 이미지 속 텍스트. 의미를 이미지로만 전달. 일러스트나 문구가 CTA처럼 보이는 것 [D2]. 데이터 읽는 화면의 밀도 저하.
- **제약:** C4.

### F11. 접근성·성능 사양을 이미지·도움 UI에 명시한다

- **패턴:** W3C WAI 이미지 지침 [A10], WCAG 1.1.1·1.4.1·1.4.4·1.4.10·1.4.11·1.4.13 [A1~A6], ARIA APG Tabs [A9], web.dev [A12~A14], KRDS 이미지·도움 패널 [K15][K5].
- **제안:** 자산마다 장식/정보/기능 분류. 장식 `alt=""`, 정보 이미지 짧은 의미형 alt, 복잡한 도식은 같은 쪽에 텍스트 동등물. 상태·도식 그래픽 대비 3:1, 색 단독 금지. 400%(320 CSS px)·200% 확대에서 가로 스크롤 없이 읽히는지 시험. 도움 패널은 좁은 폭에서 모달로 전환하고 Esc·포커스 복귀. 탭 키보드는 KRDS(Tab·Enter), APG(방향키), GOV.UK(방향키 제거) 사이에서 실제 보조기술로 시험해 결정. 홈 히어로는 즉시 로드 + `fetchpriority`, 폴드 아래는 lazy, `width`·`height` 명시, `srcset`, SVG 우선.
- **피할 위험:** LCP 이미지 lazy-load, 레이아웃 시프트, 호버 전용 도움말, 모달 포커스 함정, 탭 상태가 색으로만 구분되는 것.
- **제약:** C4.

### F12. '추천' 어휘·기본값·정렬이 결론처럼 읽히지 않게 하고, 성과는 이해로 잰다

- **패턴:** 자동화 편향 [C9], 기본값 효과 [C10], 팀의 기존 중립 규칙(예: 자원 기본 정렬은 이름순, 등록 일정 겹침에 추천 점수를 붙이지 않음) [X2].
- **근거:** 의사결정 지원이 불완전할 때의 편향은 초심자·전문가 모두에게 나타나고 훈련·지시로 막을 수 없다 [C9]. 기본값 효과는 크고(d=0.68) '선택 설계자의 권고'로 읽힐 때 더 강하다 [C10].
- **제안:** 용어를 구분한다. "처음이라면 이 순서"(절차 안내)는 허용, "추천 시기·추천 주제·적합"(내용 안내)은 금지. 기본 탭·정렬·강조색·아이콘이 순위처럼 읽히지 않는지 점검한다. 성과 지표는 5초 이해도, 첫 클릭 정확도, 도움 패널의 발견·닫기·재호출, 탭 이동 순서 분포(자유 이동이 유지되는지), 키보드·확대 과업 성공으로 잡고, 완료율·체크 개수는 지표로 삼지 않는다(팀 원칙). 분석 이벤트는 기존 분석 정책(동의·개인정보)에 맞춘다.
- **피할 위험:** '추천'이 내용 판단으로 읽히는 것. 첫 탭·첫 정렬이 우열로 읽히는 것. 완료율 KPI가 완료 압박 UI를 낳는 것.
- **제약:** C1.
