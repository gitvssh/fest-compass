# FEST Compass 실데이터 기반 고도화 계획

승인일: 2026-09-07. 사용자는 공모전 완성도와 실무 활용성을 같은 비중으로 추진하고,
관광데이터를 이용해 축제의 현재·과거 현황과 향후 전망, 운영 결정, 기록과 장기 운영을
연결하는 플랫폼 및 실제 축제 한 곳의 샘플 구현을 승인했다.

## 현재 제품 목표와 우선순위 — 2026-09-08 명확화

주 사용자는 지자체 축제 담당자다. 자기 지역의 관광정보를 지도·차트로 조회하는 일이 1차 요구,
주변의 현재 축제와 과거 회차를 비교검색하는 일이 2차 정보 수요라는 사용자 가설을 검증한다.
최종 목표는 근거를 바탕으로 올해 축제의 아이템·장소·시기·예산·준비 규모를 기획하는 것이다.

[제품 마일스톤 M1~M6](../design/07-region-planning-milestones.md)를 우선순위·완료 기준의 정본으로 삼는다.
D0 v3 검토 뒤 사용자 승인으로 [M1 전국→지역 조회와 근거 보관](20-region-explorer.md)의 첫 구현·검증을 추가했다.
[검수 안내](../review/2026-09-planning-review.md)를 시작점으로 삼는다.
M1 지역별 검증을 이어가며 [M2 주변·과거 비교검색 첫 기능](21-festival-comparison.md)을 추가했다. 다음 제품 단계는 M3 기획 대안이다.
M4 예산·준비 규모 → M5 기획안·결정 → M6 결과 재사용에는 기존 운영 기록 기능을 연결한다.
추가 모델 정확도 연구는 뒤로 미룬다. 현재 `/workspace`는 개인 운영 기록의 기반이며,
지도에서 공공데이터를 선택해 축제 기획을 결정하는 전체 제품 MVP는 아직 개발 필요다.

## 기존 작업 절차 7단계와 완료 기준

아래는 조사·설계·구현·검증 절차이며 제품 기능 마일스톤과 구분한다. M1~M6에 이 절차를 적용한다.

| 단계 | 작업 | 산출물 | 다음 단계 기준 |
|---|---|---|---|
| 1 | 기획·코드·데이터·화면 현재 점검, 실무 판단 질문 정의 | 현재 상태·가설·우선순위 | 핵심 기능에 사용자·문제·데이터·성공 기준 연결 |
| 2 | API 실값·기간·지역·갱신·결측 검증, 후보 2~3곳 비교 | 데이터 품질 보고서·샘플 선정 근거 | 핵심 데이터 또는 명시적 대체 방법 확보 |
| 3 | 예측 대상·단위·시점 확정, 과거 시점 재현, 운영 계산 검증 | 단순 기준 대비 예측 평가·계산 근거 | 기능별 제공 범위와 확보할 자료 확정 |
| 4 | 실무 의견과 증거로 기획·기능 우선순위 확정 | 개정 기획·기능·인수 기준 | 샘플의 핵심 가치와 구현 범위 확정 |
| 5 | 실제 값·결측을 사용한 화면 설계와 과제 수행 관찰 | 화면 시안·데이터 연결·사용성 결과 | 수치의 의미와 다음 행동 이해 |
| 6 | 실제 축제 한 곳의 전체 흐름 구현 | 샘플·수집 절차·회귀 검증 | 과거→현재→향후 계획→결과 추적 가능 |
| 7 | 공모전·실무 평가, 다음 개발 정리 | 검증 보고서·시연·후속 목록 | 검증 성과와 남은 가설 구분 |

## 일정 가정

2026-09-07 우선순위 변경: 사용자는 모델 정확도 개선보다 화면 구성·기능 개발과 MVP 전체 흐름
완성을 우선한다고 명시했다. 3단계의 추가 모델 연구는 보류하고 기존 모델·겨울 시험을 유지한다.
4~6단계의 [개인 작업공간](../design/06-mvp-workspace.md)을 먼저 제공한 뒤 실제 사용 과제로 피드백을 받는다.
인증·공동 저장과 현장 효과 검증은 별도 후속이며, 개인 작업 흐름 완성을 7단계 전체 완료로 표시하지 않는다.

4주 집중안: 1주 현재 점검·데이터·후보, 2주 예측·기획, 3주 화면·핵심 구현,
4주 전체 흐름·검증·발표. 정확한 제출일과 팀 가용시간은 별도 확인 대상이다.
외부 자료·인터뷰 대기는 독립적인 데이터 조사와 구현을 막지 않는다.
자료가 없다는 이유로 실측이나 예측 성능을 만들어내지 않는다.

## 데이터 검증 기준

- API 인가, 정상 응답, 비어 있지 않은 표본, 전체 수집, 제품에 쓸 수 있음은 각각 구분한다.
- 데이터마다 출처, 지표 정의, 집계 단위, 지역코드, 조회기간, 수집 시점, 갱신 지연,
  누락·중복, 이용 조건, 호출 예산과 해석 한계를 기록한다.
- 최신 공개 통계를 실시간 현황으로 표현하지 않는다. 지역 방문자와 축제 입장객을 분리한다.
- 공식 공급자 예측, 자체 모델 예측, 사용자 가정, 실측을 구분한다.
- 과거 재현은 당시 공개되어 있던 데이터만 사용한다. 현재 API의 미래 집중률을 과거 정답으로 쓰지 않는다.
- 후보는 반복 개최·과거 자료·KTO 연결·운영 문제·실무 접근 가능성으로 비교한다.
  조회 표본이 확보됐다는 이유만으로 최종 샘플로 선정하지 않는다.

## 예측·운영 기능 기준

- 예측 목표는 유지한다. 지역 방문 규모·축제 입장객·시간대별 혼잡을 별개 문제로 정의한다.
- 전년·요일·계절 기준과 시간 순서 평가로 비교하고 오차와 불확실성, 과소·과대 추정 영향을 기록한다.
- 단일 축제의 연간 총계 몇 개는 학습자료 충분성의 증거가 아니다. 필요하면 비교 가능한 유사축제 자료를 검토한다.
- 셔틀·인력·회차 변경과 비용·처리량·대기·수용량 사이의 관계는 필요한 운영자료와 계산식으로 검증한다.
- 축제와 개최회차, 자료·예측 버전, 결정 당시 입력, 실측 정의를 장기적으로 보존한다.

## 사용자 검증과 운영

팀이 확보한 실무자 3~5명을 대상으로 판단 과제, 입력 부담, 완료시간, 지표 이해도를 관찰한다.
자료 확보와 인터뷰 미실시는 미검증으로 남긴다. 공개 자료 재현은 현장 검증을 대체하지 않는다.
공개 편집에는 인증·권한 검증이 필요하며, 운영 ADR을 후속 결정 없이 변경하지 않는다.

단계 종료마다 확인 사실, 남은 불확실성, 유지·변경·보류할 기능과 다음 작업을 기록한다.
세션을 넘는 현재 상태는 `.ai/projects/fest-compass-evolution/STATE.md`에서 확인한다.

## 2026-09-07 후보 선정 진행

후보 3곳의 2023~2025년 공개 자료를 비교해 [논산딸기축제를 개발 샘플로 선정](05-festival-selection.md)했다.
1차 예측 지표는 [논산시 일별 외지인 방문 추세](06-forecast-contract.md)로 정의했다.
시군구 API의 14개 선택일 조회는 성공 10·empty 4이며, 연속 다년 자료와 당시 공개본은 미확보다.
다음 작업은 연속 수집·갱신 지연 검증과 단순 기준 모델 비교다. 2·3단계 전체 완료는 아니다.

## 2026-09-07 첫 예측 모델 진행

후속 구현으로 논산시 2023~2025년 1,096일을 모두 수집하고, 과거 이력으로 계수를 학습하는
회귀 모델과 기준 2개를 시간 순서대로 비교했다. [실험 설계](08-model-experiment.md)와
[실제 오차·검증 결과](09-model-validation.md), `/forecast`의 2025년 사례 화면을 제공한다.
기본 공개 지연 가정에서 2025년 선택된 208일의 평균 절대오차는 선정 기준보다 12.4~18.2% 작았다.
그러나 축제 4일의 방문 증가를 과소예측했고 구간 포함률도 목표에 못 미쳤다.
현재 개정자료 실험이며 당시 공개본 재현·향후 발행 예측·실무자 검증·전체 흐름 구현은 남아 있다.

## 2026-09-07 사전 예측 기록 진행

[2026년 자료와 시점별 보존·발행 기능](10-prospective-records.md)을 추가했다.
최신 자료는 8월 8일, 이후 29일은 누락이다. 이전 수집과 겹친 31일의 외지인 값·품질 변경은 없었으나
실제 공개 지연은 아직 알 수 없다. 일반 날짜의 D-7·D-28 예측 2건을 실제 발행 시각·입력·계수와 함께 저장했다.
`/forecast/records`에서 조회 기준·누락·예측과 결과 대기를 확인한다.
반복 실행 명령은 준비됐지만 예약 실행 연결, 실제 결과 도착 뒤 평가, 다음 축제 회차 발행은 남아 있다.

## 2026-09-07 매일 수집·결과 확인 연결

[매일 09시 자동 처리](11-daily-automation.md)를 운영 서비스에 연결하고 첫 실행과 공개 화면을 확인했다.
실제 7회 조회에서 최근 90일 중 61일 확보·29일 누락이며, 기존 예측 2건을 보존했다.
공개 `/forecast/records`는 저장된 최신 수집·예측·결과 대기를 읽으며 앱 재빌드 없이 갱신된다.
10월 검증 창의 D-7은 9월 28일 발행 예정으로 등록했다. 다음 날 실행과 실제 정답 도착은 계속 관찰한다.

[축제·공휴일 입력과 다음 평가 계획](12-calendar-model-plan.md)도 정리했다.
새 모델은 개발 필요하며, 2026-11-05~2027-01-31 목~일 13개 창의 사전 비교를 계획한다.
공휴일을 포함한 새 평가와 2027년 24일 엑스포에 맞는 별도 계약, 현장 운영·실무자 검증이 남아 있다.
이번 자동 연결을 7단계 전체 완료나 축제 예측 정확도 검증으로 표시하지 않는다.

## 2026-09-07 달력 모델 개발과 겨울 시험

[공휴일·축제 모델 개발](13-calendar-experiment.md)에서 공식 출처 15개로 달력을 검증하고,
과거 1,316일로 네 후보를 학습했다. 같은 개발 날짜 540일에서 공휴일 후보의 MAE는 v1보다
D-28 11.6%, D-7 10.6% 작았다. 이미 본 개발 자료이며 새 사전 시험의 성능은 아니다.
축제 입력 후보는 일정 미확보로 제공일이 줄고, 첫 2024년 축제 발행에는 학습 가능한 축제 정답이 없었다.
축제일 12일의 개선을 새 회차나 24일 엑스포에 일반화하지 않는다.

공휴일 후보와 v1·B1·B2의 겨울 시험 26건을 고정하고 매일 처리에 연결하는 코드를 구현했다.
10/8 최초 발행, 60일/90일 정답 고정, 미실행·미확보 보존과 공개 `/forecast/calendar`를 검증했다.
운영 등록·배포 증거는 13번 문서에 기록한다. 실제 향후 결과와 현장 운영 검증은 계속 남아 있다.

## 2026-09-07 축제 학습 선행 자료 보강

[2022년 방문 이력 365일을 추가](14-festival-history.md)해 2023년 축제 정답 5일도 학습했다.
같은 날짜에서 기존 결합 모델 대비 평균 오차는 3.7~5.7% 줄었지만, 개선은 2024년에 집중됐고
2025·2026년 축제일은 악화됐다. 회차별 결과와 2023년 제외 민감도를 보는 `/forecast/history`를 구현·검증했다.
소스는 main에 게시됐으나 이미지 보관 한도 초과로 첫 배포가 실패했다. 이후 사용자가 오래된 이미지 4개 정리와 기존 자동 정책 연결을 승인했다. 실제 복구 증거는 [배포 기록](../ops/forecast-history-release.md)에 남긴다.
2022년 비대면 중심 행사는 현장 축제 정답으로 합치지 않았다. 기존 겨울 시험은 유지한다.
최근 회차 악화 원인과 비교 가능한 축제 표본 검토는 사용자의 우선순위 변경으로 뒤로 미룬다. 향후 결과·현장 운영 검증은 남아 있다.

## 2026-09-08 MVP 전체 개인 작업 공개

사용자가 승인한 이미지 정리와 자동 보관 정책 연결을 마치고 이력 비교 화면의 배포를 복구했다.
이어 [MVP 개인 작업공간](15-mvp-journey.md)을 공개해 자료 확인부터 운영안 비교·결정·현장 기록·
결과 보고·다음 회차를 연결했다. 파일 보관·복원과 브라우저 자동 저장을 포함하며, 공개 환경에서
전체 동선을 검증했다. 기존 서버 쓰기 차단과 예측 모델·겨울 시험은 유지했다.
