# 최신 자료 점검과 사전 예측 기록

후속 상태: 이 기록 이후 [매일 수집·결과 확인의 운영 연결](11-daily-automation.md)을 완료했다.
아래는 연결 전 단계의 검증 기록이다.

검증일: 2026-09-07. **조회 시점별 자료 보존, 대상일 전 예측 발행, 이후 관측과 비교하는 기능은 사용 가능하다.**
`/forecast/records`에서 자료 기준일·누락과 저장된 예측을 읽을 수 있다.
반복 실행용 명령은 준비됐지만 예약 실행은 연결하지 않았다. 다음 논산딸기축제 회차의 일정 근거와
축제 효과 모델·현장 운영 검증은 남아 있다. 이번 두 예측은 일반 날짜의 사전 검증이다.

## 1. 새로 확인한 실제 자료

출처는 [한국관광공사 기초지자체 방문자 API](https://www.data.go.kr/data/15101972/openapi.do)의
`locgoRegnVisitrDDList`다. 논산시 `44230`, 외지인 `touDivCd=2`를 예측 대상으로 유지한다.
통신 기반 지역 추정치이며 축제장 계수나 시간별 혼잡으로 치환하지 않는다.

| 항목 | 이번 조회 결과 |
|---|---|
| 조회 기간 | 2025-12-01~2026-09-06, 280일 |
| 새 수집 | 전체 페이지 26회 호출, 설정 상한 45회 이내 |
| 품질 | 사용 가능 251일·누락 29일·오류 0일. 지표 3종은 별도 보존 |
| 최신 관측 | 2026-08-08. 조회일 기준 30일 전 |
| 누락 | 2026-08-09~09-06. 정상 응답에서 논산 값이 제공되지 않음 |
| 앞선 수집과 겹친 기간 | 2025년 12월 31일분. 외지인 값·품질 차이 0건 |
| 합친 범위 | 2023-01-01~2026-09-06의 1,345일 중 1,316일 확보. 기간 내부 누락 0·최근 누락 29 |
| 시점 | 마지막 API 페이지 수집 2026-09-07 18:27:50.943 한국시각, 자료 생성 18:27:51.234 |

[새 수집본](evidence/2026-09-07-nonsan-current-history.json)의 자료 버전은
`7a01f2473f537abbaaff47a436f944242fb7981ef2053b897fa658741a28eb72`다.
수집기는 29일의 누락을 담은 완전한 조회 기록을 저장한 뒤 종료 코드 **1**을 반환했다.
API 실패나 전체 날짜 확보 성공으로 분류하지 않으며, 빈 값을 0으로 채우거나 자동 재시도하지 않았다.

동일 날짜 재조회는 같은 날 수행한 두 수집본의 비교다. 개정이 없다는 장기 증거가 아니다.
이 두 수집본에는 `missing → complete` 전환이 없어 제공 시점 관측 구간도 0건이다.
`sourcePublishedAt`은 계속 null이다. **자료 기준일이 30일 전이라는 사실은 공개 지연 30일의 증거가 아니다.**
공급자 포털의 갱신 안내를 API의 실제 제공 시각으로 대신 기록하지 않는다.

## 2. 시점별 보존과 예측 발행 규칙

- 수집본을 불러올 때 자료 해시, 날짜·지역·지표값, 품질 합계, 모든 페이지의 건수·시각·출처 참조를 검사한다.
- 같은 날짜에 여러 수집본이 있으면 그 시각까지 수집·조립 완료된 최신 관측 버전을 사용한다.
  나중의 누락·오류는 이전 값보다 우선한다. 과거 값으로 조용히 대체하지 않는다.
  같은 캐시의 재조립은 새 API 관측으로 세지 않는다.
- 자료 버전은 출처·범위·페이지·값의 해시다. 별도로 파일 전체 해시의 보관본을 만들어 생성시각까지 고정한다.
  예측 입력 ID는 `자료 버전/날짜/2`이고, 보관본 참조·학습 계수·표준화·학습/입력 ID를 예측 기록에 남긴다.
- 대상은 1~4일이다. `regional-check`는 일반 날짜 검증, `festival`은 실제 회차다.
  후자는 운영자가 확인한 일정의 HTTPS 출처와 공개시각을 요구한다. CLI는 URL의 내용·공식성을 자동 인증하지 않는다.
- 시작 28일/7일 전의 한국 날짜, 09:00 이후에만 새 예측을 발행한다. CLI에 과거 발행시각을 지정하는 옵션은 없다.
  늦게 실행했으면 실제 처리 시작 시각과 지각 시간을 저장한다. 09:00 발행으로 소급하지 않는다.
- 같은 `request-id`를 다시 실행하면 최초 기록을 반환한다. 같은 ID로 대상·모델 설정을 바꾸면 거부한다.
  다른 설정·의도적 재발행에는 새 ID가 필요하다. 이미 발행된 기록을 삭제해 다시 만들지 않는다.
- 파일을 다 쓴 뒤 배타적으로 연결해 동시 실행의 덮어쓰기·부분 파일 노출을 막는다.
  이는 애플리케이션의 덮어쓰기 방지이며 외부 시각 인증이나 보안 저장 장치의 불변성 보장은 아니다.
  보관 디렉터리와 코드 버전을 함께 백업·Git 보존한다.

모델은 첫 실험의 `nonsan-direct-ridge-v1`, 규제 강도 100, 입력 지연 35일을 유지한다.
새 2026년 자료로 후보나 강도를 다시 선택하지 않고, 실제 발행 전에 확보한 과거로 계수만 다시 학습했다.
35일은 기존 실험과 연결하기 위한 모델 설정이며 측정된 공개 지연이 아니다.
최신 관측이 60일보다 오래됐거나 마지막 수집이 7일보다 오래됐으면 값을 내지 않는다.
이 두 상한은 오래된 자료를 사용하는 것을 막기 위한 개발상 제한으로, 성능을 보장하는 임계값은 아니다.
학습 이력·최근 입력이 부족한 경우에도 null과 사유를 보존한다.

과거 학습 예제는 현재 확보된 개정본을 쓴다. 이번 발행 입력이 실제 사전 확보됐다는 사실이
2023~2025년 당시 공개본 재현을 가능하게 하지는 않는다.
기존 명목 80% 구간은 시험 포함률이 부족했으므로 이번 발행에서는 **구간 제공을 보류**한다.
축제·공휴일에 따른 추가 유입은 아직 별도 학습하지 않았다.

정답은 평가 시각까지 확인된 최신 지역 추정치이며 공급자의 최종 확정값을 보장하지 않는다.
나중에 값이 개정되면 새 사후 기록을 추가해 이전 평가를 남긴다.

## 4. 재수집·발행·사후 비교 절차

Node 24.20.0 / npm 11.19.0, WSL. 다음 명령은 `apps/web` 기준이다.
키는 기존 비공개 환경 설정으로 전달하고 인수·로그·보관본에 넣지 않는다.
새 수집에서는 **새 캐시와 출력 경로**를 사용한다. 같은 캐시는 실패 재개용이므로 재조회가 되지 않는다.
최근 90일을 반복 조회하면 지연 제공과 최근 개정을 관찰할 수 있지만 더 오래된 개정은 별도 재조회가 필요하다.

```bash
# 다음 실행의 실제 조회 범위를 정한다. 예시는 2026-09-08에 실행할 때의 범위다.
npm run data:collect-history -- --start 2026-06-10 --end 2026-09-07 \
  --cache output/nonsan-20260908 --max-calls 20 --output output/nonsan-20260908.json
```

종료 코드 0은 모든 조회일 확보, 1은 누락/오류를 포함한 저장본일 수도 있다.
출력 파일이 없는 실패는 입력으로 넘기지 않는다. 파일이 있으면 품질과 메타데이터를 점검한다.
새 자료를 추가할 때 과거 파일을 덮어쓰지 않고, 겹친 날짜의 이전 수집본까지 함께 넘긴다.
API 인가·호출 한도 오류는 제공 대기로 바꾸지 않는다. 실행별 상한은 공급자의 전체 잔여 할당량이 아니다.

```bash
forecast_store=../../docs/validation/evidence/prospective
forecast_old=../../docs/validation/evidence/2026-09-07-nonsan-history.json
forecast_current=../../docs/validation/evidence/2026-09-07-nonsan-current-history.json

# 보관된 입력으로 두 예측을 다시 학습·계산하고 두 사후 기록과 화면 요약까지 대조한다. API 호출 없음.
npm run forecast:records -- verify --store "$forecast_store" \
  --snapshot "$forecast_old" --snapshot "$forecast_current" --summary data/nonsan-prospective-summary.json

# 이미 발행된 동일 요청은 날짜가 지나도 원본 반환. 새 요청은 실제 발행일에만 허용.
npm run forecast:records -- issue --store "$forecast_store" \
  --snapshot "$forecast_old" --snapshot "$forecast_current" \
  --target ../../docs/validation/evidence/targets/nonsan-20260914.json \
  --request-id nonsan-20260914-d7-v1 --horizon 7

# 새 자료가 확보된 뒤 실행. 관측 전이라면 대기 상태를 저장하며 정답을 만들지 않는다.
npm run forecast:records -- assess --store "$forecast_store" \
  --snapshot "$forecast_old" --snapshot "$forecast_current" --snapshot output/nonsan-20260908.json \
  --request-id nonsan-20260914-d7-v1

# 파생 화면 요약만 갱신. 원래 예측·사후 기록은 그대로 보존한다.
npm run forecast:records -- export --store "$forecast_store" \
  --snapshot "$forecast_old" --snapshot "$forecast_current" --snapshot output/nonsan-20260908.json \
  --output data/nonsan-prospective-summary.json
```

예약 실행을 연결할 때 수집 → 품질 검사 → 발행 대상일 확인 → 사후 비교 → 요약 생성 순서를 사용한다.
발행일 전후 임의 날짜에 실패한 발행을 반복하지 않는다. 10월 검증 창의 D-7은 2026-09-28이다.
신규 ID `nonsan-20261005-d7-v1`와 같은 10월 대상 파일·`--horizon 7`로 해당 날짜에 발행할 수 있다.
공개 페이지에서는 API 호출·모델 학습·파일 쓰기를 실행하지 않는다. 요약 갱신 후 앱 빌드·게시가 필요하다.
이번에는 호스트 예약 작업이나 클러스터 수집 작업을 설치하지 않았다.

원래 수집 캐시와 브라우저 캡처는 정본 체크아웃의 Git 제외 경로
`output/forecast-vintages-20260907/`에 보관한다. 재현에 필요한 선택 지역 자료·모델·평가·요약은 위 Git 산출물에 포함한다.

운영 배포와 실무자 과제 관찰은 실행하지 않았다. 다음 작업은 아래 순서로 진행한다.

1. 일별 수집·결과 확인의 예약 실행 환경을 연결해 실제 제공 전환과 개정을 관찰한다.
2. 축제·공휴일 효과 입력의 공개 근거를 확보하고 다음 모델의 새 평가 계획을 고정한다.
   2025년은 이미 평가에 사용했고 2026년의 이번 수집 구간은 재학습 입력으로 사용했으므로 새 미열람 시험으로 주장하지 않는다.
   아직 관측하지 않은 향후 날짜의 사전 발행·평가는 별도로 축적한다.
3. 새 날짜에서 구간 보정을 검증하고, 확정 일정이 확보된 다음 축제 회차의 사전 발행을 등록한다.
4. 지역 예측을 현장 운영 판단으로 연결하는 데 필요한 계수·운행·대기·비용 자료와 사용자 과제를 확보한다.
